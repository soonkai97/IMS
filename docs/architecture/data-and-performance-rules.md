# Data access, concurrency and performance rules

These are standing rules for every feature. Most are enforced by tests (architecture tests, integration tests, the smoke test).

## 1. Standard audit columns on every table

Every table carries the same six columns. They are properties of the Domain base class `AuditableEntity` and are stamped by the
persistence layer on save, never by use cases.

| Column | Meaning |
|---|---|
| `REC_DELETED` | Soft-delete flag. Rows are never physically deleted (an archive job may remove them later). |
| `REC_CREATOR` | Id of the user who created the row. Null when the system did (seed, background work). |
| `REC_CREDATE` | Creation time, UTC (database default `SYSUTCDATETIME()`). |
| `REC_REVISOR` | Id of the user who last changed or deleted the row. |
| `REC_REVDATE` | Time of the last change or delete, UTC. |
| `ROW_VERSION` | `rowversion`: optimistic-concurrency token. |

- A delete of a tracked row becomes `REC_DELETED = 1`. A global query filter hides deleted rows from every query.
- Unique indexes are filtered `WHERE [REC_DELETED] = 0`, so a deleted barcode, SKU or link row never blocks its re-use. The one exception is the public id
  (`PublicEntity.PublicId`, section 9): `UX_<Table>_PublicId` is NOT filtered, because an id must never be handed out twice.
- The stock ledger and the audit log carry the columns but are never updated or deleted (triggers enforce it) and have no filter.
- `AuditableEntity` is in `Ims.Domain/Common/Models`; the mapping is `ConfigureAuditColumns` in `AppDbContext`.
- Row-level audit (the `AuditLogs` table) records before/after values for master and security data. Business events (posting, approval,
  login) are recorded explicitly. Both commit in the same transaction as the change.

## 2. SQL injection

- All data access is EF Core LINQ or Ardalis specifications: values are always parameters. Raw SQL and ADO.NET commands are banned
  (`DataAccessSafetyTests`); the one exception is the lock helper, which uses `SqlQuery<int>($"...")` (interpolated = parameterised).
- Sort keys are enums (whitelists); text filters use `Contains`/`StartsWith`, which EF escapes.

## 3. No cartesian explosion

- The DbContext uses split queries by default: each collection is its own query, rows are never multiplied.
- A single query that includes two or more collections throws (`MultipleCollectionIncludeWarning` is an error); `AsSingleQuery()` is banned
  by an architecture test.
- Read models use reference joins (many-to-one) and aggregates (`SUM`, `COUNT`) in SQL, not loaded collections.

## 4. Complexity (aim for O(1) per request, never O(n) in the data)

| Need | How |
|---|---|
| Current stock of a product | one row in `StockBalance` (read model kept by posting), not a sum over the ledger |
| Next document number | one sequence row per type/warehouse/month |
| Lookup by SKU / barcode / document number / id | unique or primary-key index seek |
| Deep paging of ledger, documents, audit | seek (cursor) paging: `cursor` / `nextCursor`, constant cost at any depth |
| Page numbers (OFFSET) | refused beyond 10,000 rows; use a cursor or a narrower filter |
| Row count | skippable (`includeTotal=false`); the count is the only O(n) part of a list |
| Summaries and totals | aggregated by SQL Server into one row (`IStockSummaryReader`) |
| Exports | capped at 50,000 rows and streamed to a file |
| Settings | read once per request (scoped memoisation) |
| In-code lookups | `Dictionary` / `HashSet`, never `List.Contains` or `FirstOrDefault` inside a loop |
| Unpaged lookup lists | hard cap of 1,000 rows |

No N+1 queries: a use case issues a fixed number of queries regardless of how many rows it touches.

## 5. Concurrency and deadlocks

- Optimistic concurrency (`ROW_VERSION`) everywhere.
- Hot data is serialised with short transaction-owned application locks (`ITransactionLocker`): postings per (warehouse, product), document
  numbers per (type, warehouse, month). Locks are always taken in a fixed order (ascending product id), so they cannot form a cycle.
- `IUnitOfWork.ExecuteAsync` retries the whole transaction on a deadlock victim (1205), lock timeout (1222) or key race, with randomised
  back-off (max 5 attempts). `READ_COMMITTED_SNAPSHOT` is on, so readers never block writers.
- No blocking async calls (`.Result`, `.Wait()`): architecture test.

## 6. Timeouts

- HTTP: 30 s default, 120 s for exports, imports and file transfers (504 ProblemDetails). The request token cancels the running SQL command.
- SQL command timeout 60 s (longer than the default HTTP timeout on purpose); lock wait 10 s.
- Kestrel: headers 15 s, keep-alive 120 s, JSON body 1 MB, uploads 12 MB.
- A client that disconnects is not an error (499, not logged as one). Database unavailable is 503, not 500.

## 7. Files (images and documents)

- Bytes are stored as physical files under `Storage:RootPath`; the database keeps only metadata (`Attachment`).
- The type is decided from the file's bytes (JPEG, PNG, WebP, PDF), never from the client's name or content type; the stored name is generated;
  size is enforced while reading (never more than 10 MB in memory); PDFs with scripts, launch actions or embedded files are refused.
- Images are stored without metadata (EXIF/GPS, XMP, IPTC, comments, bytes after the end marker) and a damaged image is refused
  (`ImageMetadataStripper`); every upload then passes `IUploadScanner` (default no-op; plug a malware scanner in there) before it reaches storage.
  Details: `docs/security/upload-scanning.md`.
- Access is decided per owner by an `IAttachmentOwnerPolicy` (warehouse scope for documents, master-data permissions for products).
- Downloads are sent inert: `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: private, no-store`.
- Back the storage folder up together with the database (docker-compose mounts it as a volume).

## 8. Paging contract

Every list that can grow returns `{ items, total, page, pageSize, nextCursor }`. Sort keys are enums. Small lookup lists (units, categories,
warehouses, approval rules) return plain arrays with a hard cap.

`nextCursor` is an opaque, encrypted string (`CursorToken`: base64url of the Data Protection output for a version byte and the 8-byte internal `Id` of the last row;
purpose `Ims.Cursor.v1` plus one sub-purpose per list; `null` on the last page). It hides the row counter (decision D2). A client passes it back unchanged as the
`cursor` query parameter of the same list and never parses it. The documents, ledger and audit lists seek on it (`Id < position`, newest first), so the plan is the
one the integer `afterId` used. A value the server did not make for that list (garbage, altered, truncated, another list, another version, a variant spelling, over
`Limits.CursorMaxLength`, or made with a key that no longer exists) is a 400 on the `cursor` field. Tests and load scripts collect cursors by walking pages; they never
build one.

**Key ring (operations).** The keys that encrypt cursors are files in the directory named by `DataProtection:KeysPath` (application name `Ims`). In Production the
setting is required and the API refuses to start without it; at start-up it protects one value, so a directory that cannot be written also stops the boot with a
message. Every instance of a deployment must point at the same persisted directory (the Docker image sets `DataProtection__KeysPath=/app/keys` and docker-compose
mounts the named volume `keys` there, which also works with `read_only: true`). Outside Production the default is `ims-dataprotection-keys` under the temp directory,
never inside the repository. The keys are secrets: do not commit, log or copy them into images. A lost or replaced directory only makes outstanding cursors fail with
a 400; clients restart from page 1 and no data is lost. The keys are not part of the SQL backup.

The order of a list is part of its contract: it is total (it ends in unique keys), so a walk through the pages never skips or repeats a row,
and the export of a list uses the very same order as its pages. The receipt/issue detail (`/api/reports/movements` and its export) is
`PostedAt DESC, DocumentId DESC, line Id` (`MovementOrder`); rows of documents posted at the same instant therefore appear newest document first, and the lines of one document in entry order.
A reversed document adds a *reversal row* per line, dated by `StockDocument.ReversedAt`; the page merges the two kinds by `At DESC, DocumentId DESC, LineId, IsReversal DESC` (`IMovementReader`). Each kind is cut to its first `offset + size` rows in its own order before the merge, so the posting rows still come from a backward scan of `IX_StockDocument_PostedAt` and the (few) reversal rows never make them be sorted in full. The order of the posting rows relative to each other is unchanged and no existing index was touched; the reversal branch has its own narrow index (`IX_StockDocument_ReversedAt`, section 9).

## 9. Indexes

Measured results, rejected proposals and how to re-run them: `docs/dba/README.md`.

- **Public ids** (GUID plan PR-3, `docs/architecture/adr-guid-keys.md`). The nine tables a client addresses (User, Warehouse, Partner, Category, Uom, Product, ApprovalRule, StockDocument, Attachment) derive from `PublicEntity`: a `PublicId uniqueidentifier NOT NULL` made by the entity when it is created (`Guid.NewGuid()`, random version 4, never set from outside), default `NEWID()` for raw inserts, and a non-clustered unique index `UX_<Table>_PublicId` with `FILLFACTOR 90`, NOT filtered by `REC_DELETED`. The integer key stays the clustered one and is the only key used for joins and foreign keys. The API flips entity by entity in PR-4 to PR-7 (see `backend.md`, Public ids); Warehouse, Partner, Category, Uom (PR-4) and User (PR-5) are flipped, the others still speak integers. `IIdMap<T>` (scoped; one query per list of ids; a soft-deleted row is not found by a client id but is still named in a response), `ByPublicIdSpec` and `PublicIdsSpec` are the look-ups. `07-maintenance.sql` rebuilds these indexes with FILLFACTOR 90 and reorganises them like the others. A duplicate public id (practically unreachable) is a 409 that says to try again (`SqlExceptionMapper`; inside `ExecuteAsync` the whole use case is simply re-run and makes a new id).
  Migration `AddPublicIds`, measured on 1,000,000 documents (plus 100,000 attachments and 50,000 products; LocalDB on a laptop, warm cache; `dotnet ef database update` end to end about 30 s of which 3 s is tool start-up; Down about 3 s in all): per table add the column as NULL with the default (metadata only, 0.02 s), give old rows an id in batches of 4,000 by clustered key (StockDocument 11.7 s, about 86,000 rows/s; the loop is ONE command, so beyond about 5 million rows in a table it passes the 60 s command timeout of the application connection; that timeout is the constant `Limits.DbCommandTimeoutSeconds`, there is no setting for it, and neither the start-up migration nor `dotnet ef` can raise it. Only the backfill resumes after a timeout (its batches are committed; a new run carries on with the rows still NULL). NOT NULL, the rebuild and the index are single statements that roll back as a whole, and would need about 24, 15 and 35 million rows to reach 60 s. For a table that big, in the maintenance window run the migration as a script without a timeout (`dotnet ef migrations script <from> AddPublicIds` then `sqlcmd -t 0`; the script has no transaction and 46 batches) or raise the constant for the window. If this becomes routine the smallest change is an optional `Database:CommandTimeoutSeconds` setting read in `AddPersistence`; not built, since no table is near the limit), `ALTER COLUMN NOT NULL` (2.5 s), rebuild the clustered index (4.0 s), build the unique index (1.7 s; 27.8 MB, 90 % full). StockDocument went from 260 MB (clustered index rebuilt) to 279 MB, and with its new index the table with its twelve indexes grew by about 47 MB (about 7 %), which fits the ADR's estimate of 29 MB of index per million rows. **The rebuild is part of the migration on purpose**: without it the 16 bytes added to every row split the pages and the clustered index doubled to 558 MB at 51 % full and 98.6 % fragmented. Log: about 400 MB per million documents (the same for one `ADD ... NOT NULL DEFAULT NEWID()` statement, which was faster, 5 s against 14 s for add, backfill and NOT NULL, but is one transaction and one long table lock; the batches keep locks short, below the lock-escalation threshold, and let the log be reused between checkpoints or log backups). Run it in the maintenance window with the API stopped (offline index operations; ONLINE needs Enterprise or Developer). Rows get a new `ROW_VERSION`, so ETags held by open tabs go stale.
- Indexes on soft-deleted tables are filtered `WHERE [REC_DELETED] = 0` (EF adds `REC_DELETED = 0` to every query, so the filtered index answers it
  for free); the append-only tables (ledger, audit log) have no query filter and get unfiltered indexes.
- An index needs a named consumer: it must show reads in `docs/dba/03-index-usage.sql` after a realistic run. Foreign-key indexes EF creates
  by default are kept; extra indexes on the posting path (ledger, document lines) need a measured read win.
- Never combine a column of the main table and `EXISTS` on another table in one `OR` (a text search over SKU, name and barcode): SQL Server probes
  the other table once per row. Resolve the exact-match side first and pass its id (`ProductSearch`).
- A sort that an index should serve ends in unique keys (`Id`, or the primary key), not in a column of another table. A report that lists child
  rows newest-parent-first (movements: document lines by `PostedAt` of the document) sorts by the parent's column, then the parent id, then the
  child id, so a backward scan of an index on the parent's column streams the first rows instead of sorting every row
  (`IX_StockDocument_PostedAt`). A filtered index skips rows its filter excludes only if the query states the same predicate
  (`PostedAt IS NOT NULL`, in `MovementFilters`).
- The child side of such a report keeps its foreign-key index and gets one narrow filtered index (`IX_StockDocumentLine_DocumentId_Live`, so the
  count and page answer EF's `REC_DELETED` predicate without reading the table). A covering index on the lines (36 MB, on the posting path) was
  measured and rejected for lack of need; see `docs/dba/README.md` section 5 for when to revisit it.
- `IX_StockDocument_ReversedAt` (filtered on live rows with a reversal time; includes Status, Type, WarehouseId, PartnerId, No) is read by the reversal branch of the movements report: a backward seek on the reversed documents instead of a lookup per reversed document. It is written only when a document is reversed, never on the posting path. Measured on the 130k-ledger-row seed with 500 reversed documents (2.5 % of posted): first page 79 reads of `StockDocument` before, 18 after (the page query as a whole 438 reads before, 225 after); page at offset 5,000: 19,102 + 1,753 reads before, 18,009 + 1,584 after. Not measured at 1M rows (the posting branch is the same query as before).
- The audit log is searched by index, never by scanning: the object filter resolves a typed fragment to a short list of known entity names (`AuditEntities.Known`, `IN` on `IX_AuditLogs_EntityType_EntityId`), the entity id (document number), user and action filters are prefix matches (`LIKE 'x%'`) served by `IX_AuditLogs_EntityId_Id`, `IX_AuditLogs_Actor_Id` and `IX_AuditLogs_Action_Id`, all ending in `Id DESC` so the newest page is the first rows of a backward seek. A `Contains` (`LIKE '%x%'`) on the audit table is not allowed.
- Low stock has one definition, `Ims.Domain.LowStockRule` (written as expressions the database evaluates), and **low means on-hand at or below the safety level** (`mvp-ux.md` 3.8: a product leaves the list when a receipt brings it ABOVE its safety stock). A balance row of an ACTIVE product in an ACTIVE warehouse is low when its quantity is below zero, or when the product has a safety level above zero and the quantity is `<=` it; that is per warehouse. A product with a safety level and **no balance row in ANY active warehouse the caller can see** is "never stocked": it is listed ONCE (quantity 0, no warehouse, `avgCost` and `value` null), not once per warehouse. Only the caller's warehouses count (an old row in an inactive warehouse does not), so a scoped caller learns nothing about stock elsewhere and the answer does not change when a warehouse they cannot see receives the product (`LowStockNeverStockedTests`); a warehouse filter leaves the never-stocked products out. (An earlier version listed a never-stocked product once per warehouse that never held it: the list grew from 68,791 to 113,221 rows on the 1M database, products x warehouses, and was replaced.) The two sets are built once, in `LowStockSets`, and the readers only add their filters and shape the rows: the low-stock list, its total, the Home count and the export (`ILowStockReader`, `LowStockQuery`) and the stock list with `lowOnly=true` and its export (`ILowOnlyStockReader`, `EfLowOnlyStockReader`); the `isLow` flag of a stock row takes its verdict from the same expression (`LowStockRule.Project`). The never-stocked set is an anti-join of the products with a safety level against the balance table (product is the first key column). Worst first: largest shortfall as a share of the safety level, then in units, then SKU and warehouse code. **Measured** on the 1M database `Ims_Perf_Qa4` (172,906 balance rows, 50,002 products, 5 warehouses; 68,050 low balances plus 160 never-stocked products = 68,210 rows for an admin, 18,321 for a user scoped to one warehouse), the statements the API sends: the count (also the Home count and the badge) 5,810 reads and 650 ms of CPU, never reads the sort; a page 5,810 reads and 1.7 s of CPU at any depth, because worst-first has to rank the whole set (page 1 and the page at offset 9,950 cost the same); the first page of the stock list with `lowOnly` the same. Wall time on this shared laptop: admin count 2.9 s, first page 2.0 s, deep page about the same; scoped to one warehouse count 0.70 s and page 0.48 s (up to twice that when the machine was busy). Shrinking the set from 113,221 to 68,210 rows did NOT make the admin's page cheaper (it was 1.66 s before): the time is the scan and join of the 173k balance rows with `Product` and `Warehouse` and the ranking, not the never-stocked rows. Accepted at this size with these figures; if it must be under a second for an admin on a database this size, rank the two branches separately (top N of each, merged in memory, as the movements report does) or add a filtered index on the low balances.
- The document search box (`GET /api/documents?search=`) matches the document number, the remark or the partner name, ignoring case. **Measured on a scratch database of 1,001,800 documents** (269,019 with a remark of 45 characters on average, 84,144 containing the dense term "delivery", 20 containing a rare one, 622 partners of which 541 contain "sdn bhd"; `docs/dba/01-seed-perf.sql` plus a set-based top-up of documents; SQL Server 2025 Express on a shared 8-thread laptop, so absolute times varied 2-3x between runs and the figures below are the minimum of 3 back-to-back runs and logical reads, which do not vary):
  - **The cost is the comparison, not the reading.** A contains-match must look at every row (it cannot seek), and under the database's linguistic collation (`SQL_Latin1_General_CP1_CI_AS`) a case-insensitive `LIKE '%x%'` costs about ten times as much CPU as the same scan by code point: a term that matches nothing took 3.1 s of CPU under the collation and **0.41 s** compared as `LOWER(col) COLLATE Latin1_General_100_BIN2 LIKE lowered pattern`; the dense term 5.0 s and 0.42 s (remark alone 0.83 s, number alone 1.4 s under the collation). Both sides are lower-cased so it stays case-insensitive (tested with accented letters). It lives in `EfDocumentTextMatcher` (Infrastructure) behind `IDocumentTextMatcher`; the Application layer only asks for "contains". A count and a page of a term that matches nothing each scan the table once, so a no-match term now costs about 2 x 0.4 s at 1M documents; `includeTotal=false` halves it. It is NOT the default for a text search: the web client has no way to show an unknown total yet, so the default stays on; the web client should send `includeTotal=false` for searches (see HANDOFFS).
  - **The partner side: a short list of ids, or a join, never a cap.** #46 resolved the ids of the partners whose name contains the text, cut the list at 200 and silently dropped the rest (a "sdn bhd" search with 350 matches missed the documents of partner 300). An `IN` list costs more with every id, measured with the case-folded test and a term that matches nothing (1.0 = no partner arm, 1.4 s of CPU): 5 ids 1.4x, 50 ids 2.7x, 200 ids 5.3x, 541 ids 7.1x (22 s under the collation); `IN (SELECT .. FROM Partner)` inside the OR 11 s (a probe per document). A `LEFT JOIN Partner` costs about 1.35x in a count whatever the number of matching partners, but inside the page query (`TOP 25 .. ORDER BY Id DESC`) the optimiser walks the documents newest first and probes `Partner` for each one: a term that matches nothing then read 1,468,993 pages instead of 26,736. So `EfDocumentTextMatcher` uses both, each where it is cheap: up to `Limits.SearchPartnerListMax` (50) matching partners, an id list on the document itself (no join in the scan); with more, the name is tested through the join. More than 50 partners matching means their documents match too, so the page finds its 25 rows after a few hundred reads and the join's weakness (nothing matches) cannot occur. The partners are matched with the very same lower-cased binary comparison as the number and the remark, so the result never depends on how many partners match (`DocumentSearchTests.A_partner_is_matched_the_same_way_whether_few_or_many_partners_match`: "AESOP" and "aesop", 1 and 61 partners); nothing is capped or refused (`Documents_of_every_matching_partner_are_found_however_many_partners_match`: 50, 51 and 350 partners; the last partner's documents are found). The partner arm still makes the COUNT dearer: 11 partners 2.5 s of CPU, 541 partners 2.7 s, against 0.66 s for number and remark only (three to four times); `includeTotal=false` skips it and the page then answers in 80-90 ms.
  - **API timings after the change** (Release build, p50 of 4 warm calls, the same 1,001,800 documents, shared laptop, admin; scoped to one warehouse is 0.5 to 2x). Without the total (`includeTotal=false`): a term that matches nothing 0.73 s, a rare term 0.66 s, the dense term "delivery" 38 ms, a name matching 11 partners 87 ms, 541 partners 80 ms; for a user scoped to one warehouse the same two slow cases take 1.23 s (no match) and 1.38 s (rare term). **With the total, which is what a call without `includeTotal` does, it takes 2 to 4 s at 1M documents** (no match 2.2 s, rare 1.4 s, "delivery" 1.06 s, 11 partners 2.5 s, 541 partners 4.5 s; scoped, rare term 3.4 s): the count and the page are each a scan, and the partner arm makes the count three to four times dearer. #46 as shipped, the same calls on the same data in an earlier and busier run (so the real gain is smaller than the ratio): no match 6.4 s with the total and 3.2-7.2 s without, rare 6.1-8.6 s and 2.1 s, "delivery" 2.1-3.9 s and 13 ms; the earlier run was 3 to 7 times worse. The default call is therefore NOT under the 1 s target at 1M documents; it is a documented follow-up, and the web client should send `includeTotal=false` with a text search (HANDOFFS).
  - **A text of fewer than 3 characters is refused with 400 "Type at least 3 characters."** (`Limits.SearchMinTextLength`, checked after trimming; blank is no search): a one- or two-letter contains-match reads a million remarks and names for matches nobody can use, and an empty page with no explanation would hide why. The number is still found by any 3 characters of it.
  - **`IX_StockDocument_Search` is removed (it was added in #46).** Candidates measured at 1M documents, case-folded predicate, admin / scoped to one warehouse, a term that matches nothing: no index: count 26,736 reads, 1,469 / 1,047 ms CPU; `(No) INCLUDE (PartnerId, Remark)`: 10,523 reads; `(No) INCLUDE (PartnerId, Remark, WarehouseId)`: 11,025 reads, 1,438 / 390 ms CPU (within the noise of the first line). Adding `WarehouseId` did not change the reads, only helped a scoped count a little. The page of a term that matches nothing or is rare reads the clustered index backwards (26,737 reads) with or without it: the optimiser expects to find 25 matches quickly and never uses the narrow index for the page. So the index cuts the logical reads of the COUNT 2.4x and nothing else, costs 86 MB (41 % of the 209 MB table) and a wider write on every document insert and every edit of a remark, and the CPU, which is what a warm server spends, stays the same. Not worth it: no index. If the table ever does not fit in memory, revisit with a cold-cache measurement.
  - Not solved by any of this: a contains-match over a million remarks is O(documents) (about 0.4 s of CPU per scan). Past a few million documents move the remark search to SQL Server Full-Text (not available on LocalDB/Express) or to prefix search, or require a date range with a text search (the date filter seeks `IX_StockDocument_CreatedAt` and the text is then tested on that window only).
  - Migration `AddDocumentReversedBy` (`ReversedBy` column, its filtered foreign-key index `WHERE [ReversedBy] IS NOT NULL`, backfill from the reversal ledger entries): run twice on the 1M-document copy with `dotnet ef database update`, 10 s on a quiet machine and 33 s on a loaded one, both including about 4 s of tool start-up (not re-measured with the filtered index, which is smaller); the table is locked for those seconds only. Two gaps stay null on purpose and the document then shows "Reversed" without a name: a reversed document that has no reversal entry in the ledger, and a document reversed by the old code during a rolling deploy.
- The balance after a ledger row (`LedgerRow.BalanceAfter`, PS-14) is **stored on the row** (`StockLedgerEntry.BalanceAfter`, `decimal(18,4)`), set when the posting or the reversal creates the entry (each strategy passes the balance after it applied the line to `PostingContext.AddEntry`), under the same per-(warehouse, product) lock and in the same transaction as the balance it follows, so it cannot be overtaken by another posting (a value derived from the current balance in separate statements could be one posting off) and a page of any depth reads it from the row: no aggregate, no extra query. The row is still never updated (the trigger stays). It is returned only when the ledger is read for one product (`productId`), as before. Measured on a ledger of 1,499,484 rows with one product of 500,020 rows (the review's hot product), per request, ON TOP OF the page itself (4 reads): the alternative, deriving it as the current balance minus everything booked after the page (three queries), sums everything newer than the page: a page in the middle (250,000 newer rows) 3,492 reads / 230-310 ms CPU, the last page (500,000 newer rows) **20,506 reads / 700-780 ms CPU** (those rows are one contiguous block here; in a real ledger they are interleaved with other products and the scan reads more); that is not "constant cost at any depth". Option (a), an index `(ProductId, WarehouseId, Id) INCLUDE (QtyDelta)`, is 45 MB (28 % of the 163 MB table, written by every posting) and only halves it: 1,926 reads / 250-280 ms CPU in the middle, 375-405 ms at the end, still linear. Option (b), summing from the shorter side, is still linear in the worst case (the middle). Option (c), stored (chosen): the page query is 9 logical reads and 0 ms CPU at every depth. Cost of (c): 9 bytes a row and one value assigned at insert. Migration `AddLedgerBalanceAfter` backfills the old rows with a running sum (`SUM(QtyDelta) OVER (PARTITION BY ProductId, WarehouseId ORDER BY Id)`) with the append-only trigger switched off for that one statement inside the migration's transaction (verified afterwards: 0 differences between the last `BalanceAfter` of every (product, warehouse) and `StockBalance`, trigger enabled, tested in `LedgerBalanceMigrationTests`). **Maintenance window**: on the 1,499,484-row ledger `Up` took 62 s (loaded machine, including 4 s of tool start-up; about 40 us a row, so roughly 4 minutes at 6 million rows), it holds a schema lock on `StockLedgerEntry` (no posting during it), and it leaves the table 98 % fragmented and twice the size (163 MB to 326 MB) because every row grew: rebuild only the clustered index straight after (`ALTER INDEX PK_StockLedgerEntry ON StockLedgerEntry REBUILD`: the other indexes do not contain the new column and are not touched; the whole-table rebuild took 38 s here, back to 154 MB). Plan for about a minute per million ledger rows plus the rebuild. Estimates, not measured here: the update logs about 0.5 KB per row (about 3 GB of transaction log at 6 million rows under the full recovery model: size the log or take a log backup first), and the window function sorts the ledger by (product, warehouse, id), roughly 30 bytes a row (about 200 MB of tempdb at 6 million rows). The column has no default: the migration adds it empty, fills it and then makes it NOT NULL, so a writer that does not know the column fails instead of recording a 0 (docs/dba/08-reconcile-drill.sql checks the stored values; docs/dba/01-seed-perf.sql fills them).
- After a migration that adds columns to a big table, rebuild the indexes (`docs/dba/07-maintenance.sql`) before measuring or going live.
- `IX_StockDocument_PostedAt` (filtered on live, posted rows; includes Status, WarehouseId) is read by the Home counts ("posted today", `GET /api/documents/counts`) and by the movements report (page, newest posting first; the report repeats `PostedAt IS NOT NULL` so this filtered index applies, and it needs the lines index above, otherwise the date-filtered report gets slower). The other counts
  (drafts, returned, approvals waiting) are served by `IX_StockDocument_Status_Type_Id`: they select a Status that only a handful of rows have.

## 10. Time

- Every instant is stored and transmitted in UTC (BR-10). EF reads `datetime2` back with `Kind = Utc` (`UtcKindConverter`, applied to every `DateTime` property by convention) and the JSON
  converter writes `yyyy-MM-ddTHH:mm:ss[.fffffff]Z`; nothing on the wire is local or zone-less. Only exports and the document-number month convert to Asia/Kuala_Lumpur (+08:00).
- "Today" for counts and date filters is the Kuala Lumpur calendar day, expressed as a UTC range (`Paging.StartOfDayUtc`).

## 11. Money and unit prices

Product-owner decisions: **money has exactly 2 decimal places and never a fraction of a cent; a cost per base unit that is derived from a pack price is a unit price with up to 4 decimals.** Quantities are neither and keep the precision of their unit (4 decimals).

| Kind | Places | Fields (API and Excel) |
|---|---|---|
| **Money** | 2, half away from zero | line `amount`, a document's and a list item's `totalAmount`, stock `value` and `totalValue`, estimated amounts, approval `amountThreshold` and the numbers of an amount-rule trigger, the audit `Amount`; the cost per ENTERED unit that a person types (`unitCost` of a document line, the template's `UnitCost`); Excel columns "Value" and "Amount" (`#,##0.00`) |
| **Unit price** (a derived cost per base unit) | 4, half away from zero | `baseUnitCost` of a document line, stock row `avgCost`, ledger row `unitCost`, movements row `unitCost`; Excel columns "Avg cost" and "Unit cost" (`#,##0.0000`) |
| **Quantity** | the unit's own | `qty`, `baseQty`, `qtyOnHand`, `stockEffect`, `balanceAfter`, `qtyThreshold` and the numbers of a quantity-rule trigger |

A carton priced 3.00 that holds 1,000 pieces costs 0.0030 a piece; shown with 2 decimals it would be 0.00. Shown with 4, the amounts built on it stay right: 1,000 pieces at 0.0030 are 3.00 (line, movement and stock value). A unit price is NOT an amount: never multiply a displayed unit price by a quantity to get an amount; use `amount` and `value`.

| Step | Rule |
|---|---|
| Input | A unit cost typed on a **receipt** by a caller who may enter cost (`cost.view`) and an approval amount threshold have at most 2 decimals; `12`, `12.5` and `12.50` are fine, `12.505` is `400` "Unit cost can have at most 2 decimal places." (`Messages.CostTooPrecise`; "An amount can have at most 2 decimal places." for a threshold), one field error per offending line (`Data.Lines[n].UnitCost`). A cost that is not used is not judged: an issue takes the average and a Warehouse staff receipt takes the last known cost, whatever the request carried. In an import file the number in the cell is read (not the text it shows, so a cell formatted `0.0` that holds 2.505 is refused, and 1,234.50 shown with a comma is accepted; a formula is read by its result) and a bad one is a row error. Negative costs are refused first (one error). |
| Line amount | **Stored on the line**, computed once: for a receipt `round(entered quantity x entered unit cost, 2)` with no division through the base unit (100,000 cartons at 10.00 are 1,000,000.00 whatever the carton holds); for a line valued at the average (an issue, a staff receipt) `round(base quantity x average, 2)`. At most 999,999,999,999,999 (`Limits.MaxLineAmount`): a typed cost above it is a 400; a line at the average is capped at it, never refused, so a caller who cannot see the average cannot learn it from an error. A base quantity above 99,999,999,999,999 (`Limits.MaxBaseQuantity`, `decimal(18,4)`) is a 400. Rounded half away from zero (`StockDocumentLine.Amount`, `Money.Amount`). |
| Document total | The **sum of the stored line amounts**, not the rounded sum: three lines of 0.015 are 0.02 + 0.02 + 0.02 = 0.06. Approval rules compare this total (a rule fires at `total >= threshold`), so an estimate of 4,999.9996 is 5,000.00 and reaches a 5,000.00 rule. |
| Entered unit cost on a line | Stored too (`StockDocumentLine.EnteredUnitCost`) and returned as `unitCost` for a line whose cost was TYPED, so reading a draft and saving it back does not re-price a line in a carton (the per-base value is `baseUnitCost`; never send it back as `unitCost`). |
| Line at the average | A line nobody typed a cost for (every issue line; a receipt saved by someone without `cost.view`) has `costFromAverage = true` (`StockDocumentLine.CostFromAverage`). Its `unitCost` in the API is **null** (there is nothing to edit); it shows the read-only `baseUnitCost` (the average) and `amount`. Saving the draft again with the cost omitted keeps the line at the average, so an average of 0.0030 over 1,000 pieces stays 3.00 (it would be 0.00 if the average per entered unit were sent back as a typed cost), and 1.2349 x 1,000 stays 1,234.90. A cost typed on the line makes it a typed cost. A web footer for a document is the sum of the API line `amount`s, not `qty x unitCost` (null for these lines). |
| Stock value | `round(quantity x average cost, 2)` per stock row (a negative balance too: -1 piece at 10.005 is -10.01); the stock total is the sum of the rounded rows, so the list and the Home tile always add up. |
| Rounding mode | **Half away from zero** (`MidpointRounding.AwayFromZero`) for everything a person sees: 0.005 is 0.01, -0.005 is -0.01, 0.00305 is 0.0031. In queries `Math.Round(x, places)` is translated to SQL `ROUND` (also half away from zero on a decimal); `MoneyPrecisionTests` pins SQL and C# together at the boundary. The internal average and cost per base unit are not money; their rounding mode is stated with the costing rule (`docs/architecture/backend.md`). |
| Inside the system | A cost per base unit (document line, ledger) and the moving average keep more places than 4 (stored with the precision stated with the costing rule); the average is not rounded before it is used, so repeated receipts do not drift. |
| Outside the system | The pipeline step that already withholds cost, `ResponseShaper`, rounds every value tagged `[VisibleWith]` that stays visible: to 2 places, or to 4 for a tag with `UnitPrice = true` (exactly the four unit-price fields above; `CostVisibilityCoverageTests` pins the list). So whatever query or reader produced a number, none leaves with more places than its kind. Where a SUM or an order depends on the rounding the query rounds too (stock total; a sort by value orders by the exact value). A displayed `avgCost` times a quantity can differ by a few hundredths from `value`, because `value` uses the unrounded average. |
| Excel | A column that needs `cost.view` or `valuation.view` is a money column (`ReportColumn.IsMoney`, with an explicit `MoneyColumn` that the architecture test checks against the gating): the writer rounds its numbers to 2 decimals and formats them `#,##0.00`, except the unit-price columns "Avg cost" and "Unit cost" (`ReportColumn.UnitPriceHeaders`), which are rounded to 4 decimals and formatted `#,##0.0000`. |
| Database | Stored amounts are `decimal(18,2)` (the line `Amount`, `EnteredUnitCost`, approval thresholds), added by migration `StoredLineAmount` plus the flag `CostFromAverage` (existing issue lines are flagged; open receipt lines get `round(entered quantity x entered cost, 2)`, or the flag and the old amount when their cost has a fraction of a cent; posted lines keep `round(base quantity x cost, 2)`, so no posted total moves). |

Existing open receipt lines (Draft, Submitted, Approved) whose cost per entered unit has a fraction of a cent (typed before the 2-decimal rule, or taken from the average): `docs/dba/16-check-subcent-costs.sql` lists them. The migration flags them `CostFromAverage` and keeps their exact cost per base unit and their amount, so opening and saving them keeps their price; their `unitCost` is null in the API. Without that flag a sub-cent cost per base unit would backfill `EnteredUnitCost` as 0.00 and the price would be lost on the next save. To give such a line a typed cost, type it. Posted, reversed and cancelled documents are history and are not touched (their totals stay as shown).
