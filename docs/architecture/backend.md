# Backend architecture

Clean Architecture, CQRS and vertical slices on .NET 10.

```
Presenter (Angular)  ->  Ims.Api  ->  Ims.Application  ->  Ims.Domain
                                            ^
                          Ims.Infrastructure (EF Core, JWT, Excel, hashing) implements Application's interfaces
```

Dependencies point inward only. `Ims.Api` references `Ims.Infrastructure` solely to register services at start-up.
Architecture tests (`tests/Ims.Architecture.Tests`) fail the build if this rots.

## Layers

| Project | Holds | May reference |
|---|---|---|
| `Ims.Domain` | Data model (entities, enums, value objects), behaviour (entity methods + factories that guard their invariants), business services (posting engine and strategies, approval policy, document-action policy, costing, availability), business rules (`IBusinessRule`), constants | nothing |
| `Ims.Application` | Use cases as commands and queries with their handlers and validators, specifications, ports (interfaces), DTOs | Domain |
| `Ims.Infrastructure` | EF Core `DbContext` + migrations, `Repository<T>`, `UnitOfWork`, JWT, password hashing, Excel (ClosedXML), seed | Application, Domain |
| `Ims.Api` | Controllers, middleware, auth policies, OpenAPI/Swagger, logging, composition root | Application, Infrastructure (DI only) |

## Vertical slices

`Application/Features/<Feature>/` contains everything for that feature:

```
Features/Catalog/
  UseCases/CreateProduct/   CreateProductCommand.cs  CreateProductHandler.cs  CreateProductValidator.cs
  UseCases/ListProducts/    ListProductsQuery.cs     ListProductsHandler.cs
  Specifications/           ProductBySkuSpec.cs ...  (Ardalis.Specification: queries as named objects)
  Contracts/                ProductDto.cs ...         (request/response records)
  Services/                 IProductWriter.cs ProductWriter.cs
  Validators/               ProductSaveRequestValidator.cs   (shared DTO rules)
```

One public type per file. Controllers are grouped the same way under `Ims.Api/Features/<Feature>/`.

## CQRS and the pipeline

`IDispatcher.SendAsync(command | query)` is the only way the API enters the Application layer.
Pipeline (outermost first): `LoggingBehavior` -> `ValidationBehavior` (FluentValidation) -> handler.
Handlers depend on interfaces only (`IRepository<T>`, `IReadRepository<T>`, `IUnitOfWork`, `ISystemSettings`,
`IDocumentNumbering`, ...). Handlers never call each other; a handler that needs another use case sends a command.

## Domain-driven behaviour

Entities have private setters and factories (`Product.Create`, `StockDocument.Create`, ...). State changes happen through
methods (`Submit`, `Approve`, `Reject`, `MarkPosted`, `MarkReversed`, `Receive`, `Issue`) so an invalid state cannot be built.
Rules that span entities are domain services, not handler code: `PostingEngine` + `IPostingStrategy` per document type
(open/closed: a new document type adds a strategy), `ApprovalPolicy` (who needs to approve and which reviewer role a document is routed to),
`DocumentActionPolicy` (the `allowedActions` the UI shows AND the ownership guards the commands enforce, so a listed action is one the API accepts),
`StockAvailabilityPolicy`, `CostingPolicy`. They are pure and unit-tested without a database.

## Public ids

An entity a client addresses derives from `PublicEntity` (itself an `Entity`): besides the integer key it has a `PublicId`, a random GUID made when the object is created and never set from outside. The integer key stays the clustered key and the key of every foreign key; the public id is what leaves the system (decision and plan: [adr-guid-keys.md](adr-guid-keys.md)). Application code looks rows up with `ByPublicIdSpec` / `PublicIdsSpec` and translates lists with the scoped `IIdMap<T>` (one query per list). The API of an entity flips to the public id in the stacked PRs 4 to 7 (on the branch `feature/public-ids-integration`, merged to main once, when the web client follows in PR-8). **Flipped: Warehouse, Partner, Category, Uom (PR-4), User (PR-5), Product (PR-6), and StockDocument, Attachment and ApprovalRule (PR-7): every addressable entity.** For a flipped entity: its route is `{id:guid}` (`ApiRoutes.PublicId`), its DTO `id` is the `PublicId`, and every field, filter and list of another entity that names it (product `categoryId` / `baseUomId` / conversions, document `warehouseId` / `partnerId`, line `uomId`, stock, ledger, low-stock and movement filters, user and session `warehouseIds`) is a GUID. The translation is at the edge: a handler turns the public ids of a request or filter into integer ids with `IIdMap<T>` (`ToInternalOrNoRowAsync` for one filter value: an unknown id becomes `IdMapExtensions.NoRow`, which matches nothing, so a filter on an id that does not exist returns an empty page exactly as before; a body reference that does not exist is still a 400) and passes only integers to specifications, readers and the domain; responses project the id from the joined row (`row.Warehouse.PublicId`), never from the integer foreign key. By-id routes look the row up with `ByPublicIdSpec<T>`; an unknown id, and a warehouse outside the caller's scope, answer 404 alike. JWT claims and `ICurrentUser` keep integer ids (warehouses and the user: the token never carries a public id). Users: `UserInfo.id` (login, refresh, me), `UserDto.id`, `PUT /api/users/{id:guid}` and the document fields `createdById` / `submittedById` / `returnedById` are the user public id; the ownership and self-approval rules compare integers only (the document DTO keeps the integer keys `CreatedByKey` / `SubmittedByKey` as `[JsonIgnore]`, like `WarehouseKey`), so a public id a client has read gives no right over a document. Audit: `AppDbContext.AuditedByPublicId` lists the entities whose audit rows are named by `PublicId` (the other entities and their business events keep the integer key until their own flip PR adds them); rows written before a flip keep their integer `EntityId`, and the audit page and its entity-id filter are text, so they show and match both. Products: `GET`/`PUT /api/products/{id:guid}`, `ProductDto.id`, `DocumentLineDto.productId` / `DocumentLineInput.productId`, `StockRow` and `LowStockAlert.productId`, the `productId` filters of the stock list, ledger, movements and their exports, and the `productId` of the insufficient-stock and reversal-blocked problems are the product public id (the problem's id is given by `ShortageNamingBehavior`, the domain exception keeps the integer to itself). Filters resolve the id to the integer ONCE per request (one seek on `UX_Product_PublicId`) and the specifications use that integer in the same predicates as before; rows project `Product.PublicId` from the product they already join, never a look-up per row; `DocumentLineDto` keeps the integer product key as `[JsonIgnore] ProductKey` for the stock of an open document. Imports still resolve products by SKU. Documents: `GET`/`PUT /api/documents/{id:guid}` and every action route (`submit`, `approve`, `reject`, `cancel`, `post`, `reverse`) take the public id; `DocumentDto.id`, `DocumentListItem.id` (the approvals inbox is the same list), `LedgerRow.sourceDocId`, the `sourceDocId` ledger filter and `ImportResult.documentId` are the document public id. A document line has no id (`DocumentLineDto.id` is gone; the lines are in the order they were entered). The list item keeps the integer position as `[JsonIgnore] Key`, the value the seek cursor is made from (the public id has no order); `DocumentsPageSpec` projects `PublicId` and `Id` from the row it already reads, the ledger spec takes `SourceDocument.PublicId` from the join it already has for the number, and the `sourceDocId` filter is resolved to the integer ONCE per request (`IIdMap<StockDocument>`). Commands carry the public id and load the document with `DocumentForUpdateSpec(Guid)`; the ownership, self-approval and scope rules still compare integers. The document business events (`document.created`, ...) keep naming the document by its NUMBER (what a person searches the audit trail for); `ApprovalRule` is in `AuditedByPublicId` (its row events name it by public id); `StockDocument` and `Attachment` are not row-audited, so the attachment events carry the attachment public id explicitly (their payloads hold no owner id) and `AuditedByPublicId` has no entry for them. `ShortageNamingBehavior` names a shortage by SKU and warehouse name, and when a soft-deleted product or warehouse cannot be named it falls back to a message with their public ids (never the integer keys). Attachments: `AttachmentDto.id` and `ownerId` (list query, upload form, response) are public ids for BOTH owner types. The owner is resolved by its type (`IAttachmentOwnerPolicy.ResolveAsync`: the document table for `Document`, the product table for `Product`, one seek on `UX_*_PublicId`), after the permission check and before the existing scope and state checks (which still work on the integer key): an unknown id, an empty id, the id of a row of the other kind and an out-of-scope document are all the same 404 of that owner type, so a product id can no longer be told from a missing one by a 200 against a 404. Approval rules: `PUT /api/approval-rules/{id:guid}`, `ApprovalRuleDto.id`. The OpenAPI test `Every_id_on_the_wire_is_a_uuid_except_the_listed_positions` checks every property or parameter named `id` or ending in `Id`/`Ids` and fails for an integer unless it is one of the listed positions (`LedgerRow.id`, `AuditLogDto.id`, the text `entityId`). Storage details and the migration measurements are in [data-and-performance-rules.md](data-and-performance-rules.md) section 9.

## Permissions and roles

Design: [adr-roles-permissions.md](adr-roles-permissions.md) (lean scope). Built so far (slices RP-1 to RP-4b; no change in what any of the five roles may do, except the accepted widening of an Administrator-only approval rule, below):

- **Catalog.** `Ims.Domain.PermissionCatalog` lists the 21 permissions: stable code, group, one-sentence description, dangerous flag, administrability-core flag, `Requires`. The `Permissions` constants name the codes; the old 15-code role-keyed map is gone (RP-4a).
- **Defaults.** `SystemRoleDefaults` holds what the five system roles get by default (the one place that names roles for rights). Nothing in `src/` reads it: the migration seeds a frozen copy, and the tests hold the seeded rows and the endpoint policies to it. The Domain policies take `ActorRights`, which `ICurrentUser.Rights()` builds from the `perm` claims of the token.
- **One computation.** `EffectivePermissions.Compute(roleGrants)` keeps the codes the catalog knows; `ActorRights` is the user id plus that set.
- **Policies by permission.** `DocumentActionPolicy`, `ApprovalPolicy.MayReview(ActorRights, isLarge)` (tier permissions `document.approve` / `document.approve.large`) and `PostingAuthority` take `ActorRights`, never a role name: ownership is `document.edit.any`, posting an approved document `document.post.approved`, the negative-stock override `stock.negative.override`. An approval rule stores a tier (`ApproverTier`: Standard or Large) and nothing else; a document that fires a Large rule is Large. `ApprovalPolicy.MayReview(actor, isLarge, rulesInForce, ...)` is the whole approval limit: routed by the tier the document was stored with, and refused to a standard approver when a Large rule is in force now. There is no rank of role names (RP-4b). The rule API keeps `roleRequired` for one release, deprecated: on a save it is mapped to a tier (Owner and Admin Large, the other three system roles Standard; `approverTier` wins and the two must agree), on a read it is the system role that holds the tier by default (Supervisor or Owner), by `ApproverTierNames`. **An Administrator-only rule is now a Large rule, so the Owner can satisfy it** (owner decision Q5): before, the rank of role names kept it for the Administrator alone; the migration writes one `approval-rules.widened` audit row naming the active rules this applies to.
- **Tables (slice RP-2).** `Role` (code, name, description, system, active; public id; soft delete; unique code and name among live rows) and `RolePermission` (role + permission code, unique per role among live rows), seeded with the five system roles and their `SystemRoleDefaults` by migration `AddRolesAndPermissions` (a frozen copy, so a fresh and an upgraded database hold the same rows). `User.RoleId` points at the user's role row (it is the only record of the role: migration `DropLegacyRoleColumns`, RP-4b, dropped the `User.Role` and `ApprovalRule.RoleRequired` strings; `User.Role` is now the navigation to the row) and `User.AllWarehouses` is a choice per person, set by the user save (`allWarehouses` in the request: left out it stays on an update and is false for a new user; only a caller who sees every warehouse may switch it on for someone). The migration seeded it true for the users of Admin and Owner, so nobody's scope moved. Users are saved with any active role in the Role table (a custom role included); the validator checks only the shape of the code and the handler asks the table. The last-administrator guard still names the Admin role (RP-6 generalises it). Only the access snapshot reads these (slice RP-3, below), and the endpoints decide by the permissions in the token it writes (RP-4a). Row-level audit covers `Role` (by public id) and `RolePermission`.
- **Rights in the token (slice RP-3).** The access token carries the rights, so nothing is looked up per request. `IAccessSnapshotLoader` reads one `AccessSnapshot` (role code and name, `EffectivePermissions`, `AllWarehouses`, warehouse ids) uncached at sign-in and at refresh, before any row is written; no snapshot (user missing or inactive, role deleted or inactive) is a 401 with no new refresh-token row, no rotation and no success audit. `TokenService` writes `sub`, `nameid`, `name`, `role` (display and audit only), one `perm` per permission, `allwh`, `wh` only when `allwh` is false, and `acv` (`ClaimNames.CurrentClaimsVersion`; `ConfigureJwtBearer` refuses a token whose `acv` is not the current one with 401, so the web refreshes silently after a release that changes the claims). The lifetime is 5 minutes (`Limits.AccessTokenMinutes`, `Jwt:AccessMinutes`). A change of role or scope applies at the next refresh (about 5.5 minutes with the clock skew); only a deactivation or a password change revokes refresh tokens, and the access token already issued runs to its expiry. `UserInfo` (sign-in, refresh) is built from the same snapshot and `/me` from the presented token's claims. There is no cache and no per-request read. **Enforcement (RP-4a):** one authorization policy per catalog code, named by the code (`RequireClaim("perm", code)`), plus the any-of policies of `AuthPolicies` (`DocumentReview`: either approval tier; `DocumentCancel`: create or either tier); `ICurrentUser.Rights()` builds the `ActorRights` of the Domain policies from the same claims. The `role` claim decides nothing: the approval tier comes from `Rights()` and the warehouse scope from `allwh` and `wh`.
- **Roles API (slice RP-5).** `GET /api/permissions` (the catalog), `GET/POST /api/roles`, `GET/PUT/DELETE /api/roles/{id}`, `PUT /api/roles/{id}/permissions`; reads need `roles.read`, writes `roles.manage`; ids are public ids; a client never sends a code (the server makes it from the name: `RoleCodes`). **A change applies at the next token refresh, at most about 5.5 minutes** (the rights ride in the token; there is no cache to clear), and the controller says so. Writes obey the same containment as the user save (`RoleContainment`): a caller grants only permissions they hold (403), changes or deletes only a role that holds nothing they lack (403) and never their own role (409); a role carries no warehouse scope, so permissions are all there is to contain. The `Role` aggregate refuses (409) to rename, deactivate or delete any system role and to replace the permission set of a role that holds every admin-core permission (the Administrator role); the roles of a caller who sees fewer warehouses than a holder are out of reach (403); a role users hold cannot be deleted or deactivated (409 with the count, no names). Names and descriptions are plain text; the permission list is capped. The delete/deactivate check and the user save both run in a transaction under one application lock (`ITransactionLocker.LockRolesAsync`, resource `roles`), so a user cannot be given a role that is being deleted; a delete is a soft delete and the grants stay as rows, hidden with the role. A permission set is validated against the catalog by exact match, with no duplicates and closed under `Requires`; the two approval tiers need nothing from each other. The permission replace needs `If-Match` (428, 409 when stale); the token is a keyed hash of the public id and the row version (`RoleVersion`), and a grant change touches the role row so the token moves (`AppDbContext.TouchRolesWithChangedGrants`). Audit: the row-level rows plus `role.created`, `role.updated`, `role.permissions-changed`, `role.deleted` (entity id: the role public id).
- **Administrability (slice RP-6).** The system always keeps at least one active user whose role is live (active, not deleted) and holds the whole administration core (`users.read`, `users.manage`, `roles.read`, `roles.manage`), a system role or a custom one: `Role.Administers`, `User.IsAdministrator`, `PermissionCatalog.AdminCoreCodes`. A write that would take the last one away is refused with 409 `LastAdminRequired`: a user save (deactivate, or a role without the core; saving yourself out of it is `CannotLockOutSelf`) and a permission replace of a role that administers (`AdministrabilityGuard`, `ActiveAdministratorsSpec` = "who is left once this write is done"). A role that users hold cannot be deleted or deactivated at all, so those two writes cannot strip anyone. **No race:** both guarded writes run in `ExecuteAsync` and take the `roles` lock (`LockRolesAsync`) as their first statement, before reading the user or the role, so two parallel writes that each remove the other administrator are serialised: one passes, the other reads the committed state and gets the 409. It is the one existing lock, never held with a stock or document lock, so the global lock order is unchanged. The wait is 5 s (`Limits.RolesLockTimeoutMs`); a lock that stays busy answers 409 `LockBusy` at once (`LockTimeoutException`, which `UnitOfWork` does not retry), and a request cancelled during the wait ends as a cancellation (504), not a 500. The password hash is computed before the transaction, never under the lock. A user whose role row is soft-deleted is still listed (the user specs ignore the global filter and apply `!RecDeleted` to the user and its warehouses) and can be moved to a live role; the API cannot create that state (a role in use is refused), a manual edit can.
- **Proof.** `tests/Ims.Domain.Tests/Identity/Oracle` holds the frozen answers of the pre-roles code; `RightsParityTests` checks the new types against them for the five roles (documented differences: the Owner approves by the large tier, the six new codes, and two posting answers that only hold together with `document.post`). `EndpointCoverageTests` checks that every policy an endpoint asks for is in the catalog exactly once.
- **No role decisions (RP-8).** `NoRoleDecisionTests` fail the build when code in `src/` (migrations excluded) calls `IsInRole` or `RequireRole`, uses `[Authorize(Roles = ...)]`, reads or writes the `role` claim (`ClaimTypes.Role`, the literal `"role"`) outside three listed files (`CurrentUser`, `ConfigureJwtBearer`, `TokenService`: display and audit only), or names a system role (`SystemRoleCodes`, or a literal equal to one of its codes) outside five listed files (the code list, `SystemRoleDefaults`, the two seeders, the deprecated `roleRequired` text of the rule and trigger responses). Each entry has a reason in the test, and an entry whose file no longer names the role fails the build, so the lists only shrink. Access comes from `perm`, `allwh` and `wh`.

## Persistence

`IRepository<T>` stages changes; `IUnitOfWork.SaveChangesAsync` commits them together with audit rows;
`IUnitOfWork.ExecuteAsync` wraps a use case in one transaction with retry. Reads use Ardalis specifications and projections.
`StockLedgerEntry` and `AuditLog` are append-only: refused by the `DbContext` and by database triggers.

## Concurrency and deadlocks

- Optimistic concurrency with `rowversion` on documents, balances and number sequences.
- One global lock order: `po:{orderId}` (creating a receipt from a purchase order, cancelling or closing the order, posting a linked receipt), document sequence, document, balances by ascending `ProductId`, ledger. Posting applies lines in `ProductId` order. The `po` lock is taken first, never after a stock lock, and never together with the `roles` or `modules` locks; nothing takes the sequence lock and then the `po` lock. The full picture for purchasing, with the `modules` lock in front, is under "Purchasing" below.
- `READ_COMMITTED_SNAPSHOT` is enabled by the first migration, so readers never block writers.
- If SQL Server still picks a victim (error 1205), hits a lock timeout (1222) or a unique key races, `ExecuteAsync` rolls back, discards tracked state and re-runs after a randomised back-off (max 5 attempts), then returns 409.
- No blocking async calls anywhere (`.Result`, `.Wait()`): enforced by an architecture test.

## Dependency injection

Each layer registers itself: `AddApplication()`, `AddInfrastructure(cfg)`, `AddPresentation(cfg)`. Handlers, helpers (`IAppService`)
and validators are found by convention. The container runs with `ValidateScopes` and `ValidateOnBuild`, so a mis-wired service fails
at start-up. Options (`JwtOptions`) are validated at start-up.

## API contract (what a generated client can rely on)

The OpenAPI document at `/openapi/v1.json` describes the wire format as it is, so a client generator needs no workaround:

- **Wire format** is defined once in `Ims.Api/Composition/WireJson.cs`: enums are strings, numbers are numbers, every instant is UTC with a trailing `Z`
  (`UtcDateTimeConverter` on the wire; `UtcKindConverter` in EF so a value is `Kind = Utc` everywhere in between).
- **Enums** are string schemas that list their values (`EnumSchemaTransformer` keeps `null` out of the shared list; nullability belongs to the property).
- **Operation ids** are `Tag_action` (controller name, action in camelCase), for example `Documents_createReceipt` (`OperationIdTransformer`). Renaming a C# action renames the client method; a test pins the ones the client uses.
- **Uploads** (`IFormFile`) are inline `string/binary` parts of a multipart body and required (`MultipartRequiredTransformer`).
- **Downloads** carry `[ProducesFile(contentType)]`; the document then declares a binary 200 body and the `Content-Disposition` header (`FileResponseTransformer`).
- **Documents** carry a concurrency token (`concurrencyToken`, also the `ETag` header). A write may send it back as `If-Match`; a stale token is refused with 409 before anything is changed (`DocumentVersion.EnsureCurrent`). Changing only the lines also moves the token (`AppDbContext.TouchDocumentsWithChangedLines`).
  The token is a keyed hash, never the raw `rowversion` (one counter for the whole database, which would let a warehouse-scoped user measure what other warehouses write; ADR guid-keys, D2): HMAC-SHA256 over the document's public id and its row version, first 16 bytes, base64url (`IDocumentVersion`, `DocumentVersion`). The same document version always gives the same string (the web compares tokens for equality), and a token of another document, an old 8-byte one or any garbage is the same 409 as a stale one. The key is HKDF-SHA256 of the symmetric JWT `SigningKey` with its own info string (`Ims.DocVersion.v1`), so there is no extra secret to manage. Consequences: `DocumentVersion` depends on that symmetric key, so a move to asymmetric JWT signing needs a separate key for it; rotating the signing key gives every open editor one 409 (all sessions end then anyway). An `If-Match` that names no version (`""`, only commas) is `428`, like a missing header; only `*` skips the check. Ledger and audit rows carry no id on the wire for the same reason; their internal key only feeds the encrypted cursor.
- A barcode lookup miss is `200 { found: false, product: null }`, not a 404 (a scan that matches nothing is a normal outcome).

## Cost and value visibility

Who may see cost and value is decided by two permissions, `cost.view` (held by default by Clerk, Supervisor, Owner, Admin) and `valuation.view` (by default Supervisor, Owner, Admin), and written once: a cost or value is tagged `[VisibleWith(permission)]` where it is declared (`Ims.Domain.VisibleWithAttribute`). The matrix is in `docs/design/mvp-ux.md` 1.4. Nothing else in the code checks a role name for this.

- **Responses.** `CostVisibilityBehavior` (a pipeline step after validation, for every request) runs `ResponseShaper` over the result: a tagged property of a caller without the permission is set to `null`, wherever it sits (nested objects, lists, pages). Tagged properties are therefore nullable `init` properties; `OnlyWhen` limits the rule to one case (an approval trigger hides its numbers only for an amount rule). Handlers see the full values: only the outermost request is shaped (`ShapingState`), so a handler that sends another command reads the complete result.
- **Audit.** `AuditPayloadScrubber` removes the keys that name a cost or value from the before/after JSON (entity properties tagged in the Domain, plus the payload keys of `AuditFields`); a payload that carries money must name its key with an `AuditFields` constant. The audit log itself is Owner and Admin only.
- **Excel.** Handlers write spreadsheets only through `IReportWriter` with `ReportColumn`s (`ReportHeaders`, `ImportTemplates`); a column with `VisibleWith` is left out, header and cells, for a caller without the permission.
- **Sorting and filtering.** An enum member tagged `[VisibleWith]` (`StockSort.Value`) is refused with `400` by `RequestGuard` for a caller without the permission, because the order would reveal the value.
- **Receipts without cost.** `IReceiptCostDefaults`: a receipt saved by a caller without `cost.view` takes the last known (average) cost per product in the warehouse, or zero for a product never stocked there, whatever cost the request carried (`StockDocument.ApplyKnownReceiptCosts`).
- **Tests.** `Ims.Architecture.Tests/CostVisibilityCoverageTests` fails when a response property, entity property, export column or sort key whose name looks like cost or value is not tagged, when a tagged property cannot be withheld, when anything but `ReportWriter` uses `IExcelWriter`, or when an audit payload names money without `AuditFields`. `Ims.Api.Tests/Tests/Visibility` asks every read, export and document command as every role and compares the money found (by name) with what the role may see.

## Costing and reversal

`StockBalance` holds quantity and the moving weighted-average cost (10 decimal places, `Limits.CostDecimals`, SQL `decimal(22,10)`, rounded half away from zero); a value is always `quantity x average`.
The cost per base unit and the average are INTERNAL numbers, not money: every amount that reaches a person is money (2 decimals, `Ims.Domain.Money`, which arrives with the money-precision change), and nothing in the API or an export shows the internal precision once the money-precision change is in.

- **Marker.** `StockBalance.LastReceiptLineId` is the document line that brought stock in last. EVERY stock-in sets it: a receipt line, a receipt at the average itself (a staff receipt takes the average as its cost) and the line of a reversed issue. An equal average is never taken as proof that nothing came in since.
- **Snapshot.** Posting a receipt line records `StockDocumentLine.AvgCostBefore`, `AvgCostAfter` and `PreviousLineId` (the marker before it).
- **Reversal** (`StockBalance.Unreceive`): while the line is still the marker, the average goes back to `AvgCostBefore` and the marker to `PreviousLineId`; otherwise the receipt's value (`qty x cost`) is taken out of the stock value and the rest is shared by the remaining units, and the marker is cleared (the recorded averages of the later receipts still contain this one); where that has no sound answer the average is kept; a first receipt whose units were issued under negative stock keeps the last known cost instead of 0. The result never exceeds `Limits.MaxCostPerBaseUnit`. The lines of one product are reversed last-posted first.
- **Range.** A unit cost is at most `Limits.MaxUnitCost` (1,000,000,000) when entered, and its cost per base unit at most `Limits.MaxCostPerBaseUnit` (999,999,999,999, the 12 integer digits of the column): a 400 (`CostTooLarge`, `CostTooLargeForUnit`), never a database overflow. `DocumentSaveRequestValidator`, the opening-stock import and `CostingPolicy` enforce it.
- **Maintenance window.** Migration `AverageCostMarkersAndCostScale` changes `StockLedgerEntry.UnitCost`, `StockDocumentLine.UnitCost` and `StockBalance.AvgCost` from `decimal(18,6)` to `decimal(22,10)` (the type's storage grows from 9 to 13 bytes) and adds four nullable columns. It rewrites the three tables under a schema-modification lock: about 3 minutes on 1.5 million ledger rows with a cold cache (independent measurement: ledger 128 s, document lines 64 s; Down about 21 s); plan a maintenance window of several minutes, scaled to the size of the ledger (a warm 1M-row LocalDB copy took 20 s, so the time depends on the cache and the disk). Stop the API; rebuild the indexes of the three tables afterwards (`docs/dba/07-maintenance.sql`). No value can overflow, because the integer part is 12 digits before and after. The migration test (`AverageCostMigrationTests`) runs Up, Down and Up again on a database that holds rows.
- **Repair.** `docs/dba/15-repair-reversal-average.sql` recomputes, once, the average of the balances that the old reversal left contaminated (report first, then `-v Apply=1`).
- `PostingEngine.FindReversalDeficits` still decides, by quantity, whether a reversal is allowed. The rule and its examples are in `docs/design/mvp-ux.md` 1.5; the tests are `ReceiptReversalCostingTests` (domain) and `ReceiptReversalCostTests` (API).

## Modules and tracking dimensions (accepted)

**Accounting export (built, PL1.6).** `GET /api/accounting/export` is a query handler that also writes: it saves one audit row per file produced (`accounting.exported`) before it answers, so no file leaves without its record. This is accepted as an exception to "a query changes nothing" because the audit row is the point of the endpoint; it is the only query that saves, and a refused request writes nothing. It asks for the permissions the file shows (`cost.view`, `masterdata.read`, `reports.read`, the `Requires` of `accounting.export`) again in the handler, reads at most `Limits.MaxExportRows + 1` rows in one statement, and refuses a period above the cap with a 400.

Optional lot/serial tracking on the ledger and switch-on modules (accounting hand-off, stocktake, batch, purchasing, sales, returns, assembly, serial) are designed in [adr-modules-and-tracking-dimensions.md](adr-modules-and-tracking-dimensions.md). Status: accepted 2026-10-19 (owner). Built: the module foundation and `accounting` (pilot slice PL1) and `purchasing` (PL2, section "Purchasing" below). The `accounting` module is dormant (OFF by default) and not part of the pilot since 2026-10-22; its code stays, nobody switches it on. Not built: the tracking dimension (lots, serials), sales and returns (PL3), stocktake (PL4). Pilot order: accounting export with the module foundation, purchasing, sales and returns, stocktake, then batch and serial; `StockBalance` and the per-(warehouse, product) lock stay as they are.

## Purchasing

Pilot slice PL2 (module `purchasing`): purchase orders, receiving against them, a reorder list. Plan, acceptance criteria and the "As built" notes: [pilot-slice-2-plan.md](../pm/pilot-slice-2-plan.md); DBA numbers: `docs/dba/README.md` sections 12 and 13; security retest: `docs/reviews/pl2-security-retest/report.md`. Code: `Ims.Domain/Purchasing`, `Ims.Application/Features/Purchasing`, `Ims.Api/Features/Purchasing/PurchaseOrdersController`. Where the plan text and the code differ, this section follows the code.

**Module and permissions.** `ModuleCatalog` lists `purchasing` (off by default). `po.read` (requires `masterdata.read`) and `po.manage` (requires `po.read`, `cost.view`, `stock.read`) belong to the module: while it is off the permission catalog omits them, a role save naming one is a 400, and a role that holds one keeps it hidden and gets it back when the module is switched on. There is no approval permission for orders: approving or rejecting uses the two tiers, `document.approve` and `document.approve.large` (policy `DocumentReview`), plus `po.read`, which the handler asks because an endpoint carries one policy. Defaults: Administrator both; Supervisor and Clerk both; Owner and Warehouse staff `po.read` only. Migration `GrantPurchasingPermissions` seeds the grants.

**Entities and tables.** `PurchaseOrder` and `PurchaseOrderLine` (migration `AddPurchaseOrders`; public id on the order, lines addressed by `LineNo` 1..n) are their own aggregate: an order moves no stock and is not a `StockDocument`, so it never appears in the documents list, the movements report or the accounting export. The order holds supplier (an active Supplier partner), one ship-to warehouse (fixed once created, it carries the number `PO-<WH>-<yyMM>-<nnnn>`, Kuala Lumpur month, from `DocumentSequence`), remark, the creator/submitter/approver/rejecter/closer with times, `RequiresApproval`, `IsLarge`, the rejection, cancel and close reasons and `CloseKind` (Received or Short). A line holds product, quantity in the unit entered, `BaseQty` (converted once at order time, BR-04), `UnitPrice` and a stored `Amount` rounded to 2 decimals half away from zero; the total is computed. Limits are those of document lines (500 lines, quantity, price and amount caps). Indexes: unique number, `(Status, Id)`, supplier, warehouse, and `(ProductId)` including `PurchaseOrderId` and `BaseQty` on the lines. The receipt link is migration `AddReceiptPurchaseOrderLinks`: `StockDocument.PurchaseOrderId` (nullable, no default, foreign key, filtered index `IX_StockDocument_PurchaseOrderId`) and `StockDocumentLine.PurchaseOrderLineNo` (nullable int, no foreign key and no index: an Approved order's lines never change and the lines are reached through their document). `DocumentType.PurchaseOrder` exists only as the key of an approval rule and a number prefix; `StockDocument.Create` refuses it.

**State machine and approval.** Draft -> Submitted -> Approved, or Draft -> Approved at once when no rule fires; a rejection (reason of 5 or more characters, by a reviewer) or a recall (by the submitter) returns a Submitted order to Draft; Draft, Submitted and Approved -> Cancelled; Approved -> Closed. Submit needs every line priced above 0 (a draft may hold 0.00, which is what a reorder draft starts with). The submit tests the order's total at cost and its total base quantity against the active `DocumentType.PurchaseOrder` rules and stores `RequiresApproval` and `IsLarge`: Standard is approved by a Supervisor, Large by the Owner, an Administrator either; nobody approves or rejects what they submitted while self-approval is off (BR-07); approve re-checks the routing against the rules in force now. Who may do what is one function, `PurchaseOrderActionPolicy`, which feeds `allowedActions`, `canAct` and the handler guards: a Draft is edited and submitted by any `po.manage` holder and cancelled by its creator (or a `modules.manage` holder, so a departed creator's draft cannot block switching the module off); a Submitted order is recalled and cancelled by its submitter; an Approved one is cancelled by a reviewer of its tier with a reason. Every transition needs `If-Match` (428 without, 409 `document_changed` when stale; the token is the keyed hash of `DocumentVersion`) and writes an audit event with actor, before, after and reason.

**Receipt link and posting.** `POST /api/purchase-orders/{id}/receipt` (policy `document.create`, and `po.read` asked in the handler) creates a Draft receipt of an Approved order that has something left: the order's warehouse and supplier, one line per order line with quantity remaining, in the order's unit, at the order's price, each carrying `purchaseOrderLineNo`. The link is set here and never changes; no request field can set or clear it (`DocumentLineInput.purchaseOrderLineNo` only names a line of the order this draft is already linked to). A save of a linked draft needs the module on and `po.read`, keeps supplier and warehouse, and every line must name an order line, in that line's unit, within what remains (400 naming the line); lines may be removed or lowered. **Received quantity is computed, never stored:** the sum of base quantities of Posted receipt lines per order line number (`IReceivedQuantityReader`, one grouped statement through the filtered index); a Draft, Submitted, Approved, Cancelled or Reversed receipt counts as nothing, so a reversal gives the quantity back with no code. **Posting a linked receipt** (`LinkedReceiptPosting`, called by `PostDocumentHandler`; an unlinked document answers at once with no query, so the frozen statement counts hold): lock `po:{id}` first, then read the module switch, the order and the received sums fresh; refuse a module that is off or an order that is no longer Approved (409 naming the status); refuse a line over what remains (**over-receipt**, 409 `over_receipt`, extension `lines` with line number, SKU, ordered, received, remaining, requested: quantities only, no money; there is no tolerance setting); run the unchanged engine; and when every line is now fully received close the order in the same transaction (`CloseReceived`, audit `purchase-order.closed` naming the poster and the receipt). **Auto-close and close short:** an order whose last quantity arrives closes itself (kind Received). `POST /api/purchase-orders/{id}/close` (`po.manage`, reason of 5 or more characters) closes an Approved order short only once something has been received (with nothing received the answer is 409 "cancel it instead", so cancel stays the one way to void an order), and not while a receipt is Draft, Submitted or Approved. Cancelling an Approved order is refused (409 naming the receipt) while a linked receipt is Draft, Submitted, Approved or Posted; Cancelled and Reversed receipts do not block it. **A reversal never reopens a Closed order;** the missing quantity comes back through the reorder list or a new order. Submitting a linked receipt re-checks module, order and remaining; approving one re-checks nothing (posting decides). A caller without `po.read` is told refusals in general words, with no order number, status or figures.

**Locks.** Purchasing adds two application locks to `ITransactionLocker`: the `modules` lock in two forms and `po:{orderId}`. Paths and their order: switching a module takes `modules` exclusively; creating an order takes `modules` shared (`HoldOnAsync`, which re-reads the switch), then the document sequence; creating a receipt from an order takes `po`, reads the order, then the sequence; cancel and close short take `po` only; posting a linked receipt takes `po`, then (in the balance loader) the stock locks by ascending `ProductId`, then writes. The module switch is only read, with no lock, at posting. The global order is therefore `modules` -> `po:{id}` -> document sequence -> document -> stock ascending, no path holds `modules` together with `po` or stock, nothing takes the sequence lock before `po`, and the lock tests prove each call (`PurchaseOrderLockTests` hold the lock from another connection and see the request wait; removing a call fails the test; two receipts racing for the last quantity over 25 rounds give one winner).

**Switching the module.** Switch-on is refused (409) while no `PurchaseOrder` approval rule is active (`PurchasingModuleEnableCheck`; migration `AddPurchaseOrderApprovalRules` and the Seeder write the two placeholder rules, RM 5,000 Standard and RM 20,000 Large, only where none exists). Switch-off is refused (409 with the count, nothing written, no audit row) while any order is Draft, Submitted or Approved (`PurchasingModuleDisableCheck` through the `IModuleDisableCheck` seam, asked under the `modules` lock); Closed and Cancelled orders are kept and shown again when the module is back on. The module gate (`ModuleGateMiddleware`, `[RequiresModule]` on the controller) answers a signed-in caller of an off module with the 404 of an unknown route before the permission is asked; anonymous stays 401. Core endpoints carry the module's fields only while it is on (`DocumentDto.purchaseOrder`, line `purchaseOrderLineNo`), and the approval-rule list hides purchase-order rules while it is off.

**Reorder rule** (`GET /api/purchase-orders/suggestions?warehouseId=`, `po.read`, one warehouse, 404 for an unknown or out-of-scope one, page/pageSize ordered by SKU). A product that is low in the warehouse (the shared low-stock rule: at or below safety stock, negative, or a safety level and no balance anywhere the caller can see) is suggested `max(2 x safety - on hand - on order, 0)` in base units; rows with 0 are left out. **On order is the remaining quantity of Draft, Submitted and Approved orders of that warehouse** (`ReorderRule.OnOrderStatuses`; Posted receipts taken off; Closed and Cancelled count 0), so a row leaves the list as soon as a draft covers it. One query serves count and page. There is no per-product order quantity, supplier or lead time; the buyer edits the quantity and nothing is ordered without a human submit.

**Cost visibility.** The order's `totalAmount`, line `unitPrice` and `amount` and the suggestion's `suggestedValue` are `[VisibleWith(cost.view)]`: absent from the payload (JSON null) for a caller without it, also in the audit payloads. Creating or saving an order needs `cost.view` (403 otherwise, besides `po.manage` requiring it in the catalog), because the price is written as sent. A receipt made from an order takes the order's price whoever creates it: Warehouse staff never see it, a unit cost they type is discarded, and the stock is valued at the order price. Quantities in the over-receipt answer are not cost and are shown to every `po.read` holder.

**The `Optional<T>` presence pattern (accounting tax fields; PL1.8 API follow-up).** `ProductSaveRequest.HsCode/SstCode` and `PartnerSaveRequest.Tin/SstRegNo` are `Optional<string>`, a struct that tells "key absent" from "key sent as null". On a save an absent key leaves the stored value unchanged (no write, no audit row); an explicit `null`, `""` or whitespace clears it; a value replaces it after the shape check; each key of a pair is judged on its own. On create, absent means none. With the module off absent and blank are nothing and a value is a 400 naming the field (`ModuleFields`). On the wire it is the bare value (`OptionalJsonConverter`) and in OpenAPI an optional nullable property (`OptionalSchemaTransformer`), so the generated types did not change. The reason: an old web bundle, a stale form or a script that never sends the four keys must not wipe values entered after the switch-on. Use it only for a field of a module that a client may legitimately omit and where omitting must differ from clearing; every other field stays a plain nullable property (a purchase-order line, by contrast, fails closed: a linked draft refuses lines without `purchaseOrderLineNo`).

**The web pattern.** Menu and routes use `requireModule(purchasing)` then `requirePermission(po.read)`; buttons are exactly the API's `allowedActions` (`submit`, `recall`, `approve`, `reject`, `cancel`, `close`, `receive`, `edit`), never a role, a permission or a status test, so a rule change in `PurchaseOrderActionPolicy` reaches the screens with no web change. `receive` is offered when the order is Approved, something remains, and the caller holds `document.create` and `po.read`; `edit`, `submit` and `post` of a linked receipt are filtered by `LinkedReceiptPolicy` (the one rule behind both `allowedActions` and the handler guards; edit needs `po.read` and the module on, submit and post need the module on). The receipt editor knows a linked receipt from `DocumentDto.purchaseOrder` and always sends `purchaseOrderLineNo`; every form sends every field; a stale copy is recognised by `code = document_changed` only. Agreement tests (`ReceiveActionAgreementTests`, `LinkedReceiptActionAgreementTests`) assert that an action is offered exactly when the API accepts it.

## Security cross-cutting (Ims.Api)

- `SecurityHeadersMiddleware` (first in the pipeline after forwarded headers/HSTS): defensive headers on every response, added at response start so errors and 429s carry them; an endpoint may override (attachments do). Values: `SecurityHeaders`.
- Sign-in transport: the refresh token is also an `HttpOnly; Secure; SameSite=Strict; Path=/api/auth` cookie (`RefreshTokenCookie`); a request that relies on the cookie must pass `CsrfGuard` (custom header + Origin/Referer in `Cors:Origins`). `AuthController` chooses body or cookie; Application handlers do not know about cookies. The deprecated body delivery is off by default (`Auth:ReturnRefreshTokenInBody=false`); the switch stays for a rollback. See `docs/security/refresh-cookie.md`.
- Ports for pluggable security adapters live in Application and get a safe default in Infrastructure (`IUploadScanner` / `NoOpUploadScanner`).
- Static web hosting headers (CSP etc.) are a proxy concern: `docs/security/web-headers.md`. Runtime scan: `docs/security/dast.md`.

## Trade-offs recorded

- Application references `Ardalis.Specification` (persistence-ignorant) but not EF Core.
- Namespaces inside a layer are flat per feature (`Ims.Application.Features.Catalog`) while folders carry the finer structure.
- Permissions are defined in code (the catalog, stable codes) and roles are configurable: the five roles of PRD 3.1 are system roles whose permission matrix is their *defaults*, not a fixed rule; custom roles and the move of roles into the database follow [adr-roles-permissions.md](adr-roles-permissions.md) (accepted 2026-10-16, lean scope). Since slice RP-4a the endpoints read the `perm` claims of the token; `tests/Ims.Domain.Tests/Identity/Oracle` pins the answers of the old role-keyed matrix so every slice can prove the default behaviour did not move (see "Permissions and roles").
