Checklist answers. Simpler way? Yes in four places, all taken: no new approve permission (D1), received quantity computed and not stored (D4), reorder is one endpoint over the existing low-stock reader and no new product field (D8), print is the browser's print view and not a PDF engine. New dependency? None. New configuration surface? None: the over-receipt policy is a fixed rule (question 1), the reorder target is a fixed rule (question 3), the approval thresholds are the existing Settings rules.

| D8 | **Reorder rule:** for a warehouse, each low-stock row (the existing `LowStockRule`) gets `onOrder` = remaining base quantity on Approved POs of that warehouse, and `suggested = max(2 x safetyStock - onHand - onOrder, 0)`; rows with 0 are left out. | D9 | **The client is regenerated inside the backend PR that changes the contract.** There are no stand-alone "contract batch" sub-slices in PL2. | PL1.3 added the drift test (`OpenApiDocumentTests.The_live_document_equals_the_one_the_web_client_was_generated_from`): any contract change fails CI until `npm run api:generate` is committed, so PL1.5 and PL1.6 folded CS7 and CS8 into their PRs. | D10 | **A receipt line names its PO line by `purchaseOrderLineNo`** (1 to n inside the PO, frozen once the PO is Approved), not by an id. ## 6. Acceptance criteria

Given / when / then, one block per sub-slice; each criterion is a named test whose name carries the requirement id.

**PL2.1 Module and permissions**
1. Given the catalog has `purchasing`, when a signed-in user calls `GET /api/modules`, then it is listed with `enabled: false`; an Administrator can switch it on with a reason and the audit event is written as for `accounting`.
2. Given the module is off, then `GET /api/permissions` omits `po.read` and `po.manage`, and a role save naming one is a 400 "not available"; a role that holds one keeps it (hidden grants), and the enable reply counts roles regaining it (the PL1.2 generated tests run over the new codes).
3. `po.manage` cannot be saved on a role that lacks `po.read`, `cost.view` or `stock.read` (closure); `po.read` needs `masterdata.read`.
4. Given a fresh and a migrated database, then Admin holds both codes; Supervisor and Clerk hold both; Owner and Warehouse staff hold `po.read` only; a role without the required permissions gets none; `Down` removes all rows; `SystemRoleDefaults` equals the rows.
5. Given a registered `IModuleDisableCheck` that reports 3 open orders, when an Administrator switches that module off, then 409 with the count, no setting change and no audit row; with 0 it is 200; with no check registered it is 200. Turning a module on is never checked.
6. Architecture: every controller of a module namespace carries `[RequiresModule]`; every endpoint guarded by a module permission is on that module's controller; `NoRoleDecisionTests` and `EndpointCoverageTests` stay green.

**PL2.2 PO core**
1. Given the module is on and a caller with `po.manage`, when they POST a PO with a supplier, a warehouse and lines, then 200 with a Draft, number `PO-<WH>-<yyMM>-0001` (Kuala Lumpur month), lines numbered 1 to n, base quantity converted (BR-04), line amount `round(entered qty x entered price, 2)` half away from zero, total the sum of the lines; one audit event.
2. Given 20 parallel creates in one warehouse and month, then the numbers are distinct and gap-free (BR-11).
3. A customer as supplier, an inactive supplier, warehouse or product, 0 lines, more than 500 lines, a quantity, price or amount above the limits, a price with a fraction of a cent: each is a 400 naming the field (all line errors, not the first).
4. Given a draft, when `po.manage` holders PUT it with `If-Match`, then the lines are replaced and the number and status are kept; a missing header is 428, a stale one 409; an Approved PO is not editable (409).
5. Given a caller with `po.read` and no `cost.view`, then list and detail carry no price, amount or total (the field is absent, not null); `CostVisibilityCoverageTests` walks the new DTOs and fails if one is not annotated.
6. Given a user scoped to warehouse A, then the list shows only A's orders, an order of B by id is 404, and a create for B is the same 400 as a document's.
7. Module off: 404 for every role on every PO endpoint, 401 anonymous. On, without the permission: 403.
8. Migration `AddPurchaseOrders`: Up, Down, Up on a database with rows; Down refuses while a PO exists; the model/snapshot test is green; the contract test passes with the regenerated client committed.

**PL2.3 PO workflow**
1. Given no active PO rule, when the creator submits, then the PO is Approved at once with `RequiresApproval` false and no approver; given a Standard rule with threshold 5,000.00 and a PO of 6,000.00, then it is Submitted and routed to `document.approve`; given a Large rule it is routed to `document.approve.large` (Owner), and a Supervisor gets 403 on it.
2. Given a Submitted PO, then the submitter cannot approve or reject it (self-approval setting as for documents), another holder of the tier can; reject needs a reason of 5 or more characters and returns the PO to Draft as "Returned"; the submitter can recall a Submitted PO.
3. Given a line with price 0.00, then submit is a 400 naming the line (D11); a draft with 0.00 saves.
4. Given an Approved PO with nothing received, then a reviewer it is routed to can cancel it with a reason; given a Draft or Submitted one, its creator or submitter can cancel; given a PO with a posted linked receipt, cancel is refused and "close" is offered (PL2.4/PL2.5 tests extend this).
5. Given an Approved PO, then a `po.manage` holder can close it short with a reason of 5 or more characters; the state is Closed with kind Short.
6. `allowedActions` for each state and role equals the policy table (a generated matrix over the five system roles); `canAct` in the list is true only for a reviewer who may act now.
7. Given `docType = PurchaseOrder` in Settings, then create/update/list work only while the module is on (400 on write, hidden in the list while off); every `DocumentType` value has its own number prefix; `StockDocument.Create` refuses `PurchaseOrder`.
8. Given a Draft, Submitted or Approved PO, when an Administrator switches the module off, then 409 "N open purchase orders: close or cancel them first"; with only Closed or Cancelled ones it is 200, the data is kept, and on again shows it.
9. Each transition writes an audit event with actor, before, after and reason; two simultaneous approvals give one 200 and one 409.
*As built in PL2.3a (branch `feature/pl23a-po-workflow`; the disable check, its lock and the race are PL2.3b):* close short (criterion 5) moves to PL2.5 with the receipts, and the refusal of cancel while a posted or open linked receipt exists (criterion 4, last part) to PL2.4, because neither can happen before the link exists. A Draft is cancelled by its creator (any `po.manage` holder edits and submits it); a Submitted order is recalled and cancelled by its submitter; an Approved one is cancelled by a reviewer of its tier, with a reason. The "awaiting approval" list filter is `status=Submitted` plus `canAct`; `DocumentCounts` does not count orders (the badge stays out of scope). In PL2.3b the race between a switch-off and an order being created is closed by the shared form of the `modules` lock in order creation (lock order: `modules` shared, then the document sequence); other transitions need no lock because the order they move is already counted as open. The two placeholder rules were first written by the Seeder only; PL2.3c adds the data migration `AddPurchaseOrderApprovalRules` (same rows, only where no purchase-order rule exists), so a database deployed by script has them too. Go-live gate: the owner reviews the placeholder amounts (RM 5,000 / RM 20,000) before purchasing goes live; they are editable data in Settings once purchasing is on.

**PL2.4 Receipt link**
1. Given an Approved PO with lines A (10) and B (5), when a user with `document.create` and `po.read` calls `POST /purchase-orders/{id}/receipt`, then a Draft receipt exists in the PO's warehouse for the PO's supplier, one line per PO line with remaining quantity above 0, in the PO's unit, cost the PO price, each line carrying `purchaseOrderLineNo`, the header the PO id and number.
2. Given the PO is Draft, Submitted, Closed or Cancelled, or has nothing left, then 409 with a sentence that says which; module off 404.
3. Given the caller lacks `cost.view`, then the receipt lines still carry the PO price, the response shows none, and after posting the ledger unit cost equals the PO price (a posting test).
4. Given a linked draft, when the user saves it, then every line names a PO line of the same PO, the base quantity of each PO line does not exceed what remains (400 naming the line), the supplier and warehouse cannot be changed, and lines may be removed or reduced; a save without `purchaseOrderLineNo` is a 400 and the link is intact; naming a PO line on an unlinked document is a 400; with the module off, carrying the field is a 400 "not available".
5. Given 6 of 10 posted through a linked receipt (the plain post, before PL2.5), then the PO shows received 6 and remaining 4 for that line; reversing that receipt shows 0 and 10. Draft, Submitted, Approved and Cancelled receipts count as nothing.
6. Given a linked receipt in Draft, Submitted or Approved, then cancel and close of the PO are 409 naming the receipt.
7. The PO detail lists its linked receipts (number, status); the receipt GET shows the PO number only while the module is on; a GET of an unlinked document issues the same SQL statements as before (statement-count test).
8. Migration `AddReceiptPurchaseOrderLinks`: nullable, no default, filtered FK indexes only (model test), Up, Down, Up with rows, Down refuses while a link exists; the DBA records the 1M-tier time of the two adds and the FK validation in `docs/dba/README.md`.

**PL2.5 Posting against a PO**
1. Given a linked receipt and an Approved PO, when it is posted, then the ledger and balances are what an unlinked receipt of the same lines gives (same rows, same average), and the PO shows the new received quantity.
2. Given the PO is Closed or Cancelled, then posting is 409 naming the status and nothing is written.
3. Given 10 ordered, 6 posted, a second receipt of 5, then posting is 409 `OverReceipt` naming the product, ordered 10, received 6, remaining 4; a staff caller sees the quantities and no money; nothing is written. A receipt of 4 posts.
4. Given two drafts of 6 against one line of 10, posted at the same time, over 25 rounds, then exactly one succeeds each round, the other is 409, and the balance equals the ledger sum (the F1 style).
5. Given parallel posts of linked receipts and unrelated issues of the same products, then no deadlock is reported (retried 1205 counts as recovered; the test asserts the final state and the lock order `po` then stock).
6. Given the last open quantity is received, then the PO becomes Closed (kind Received) in the same transaction with an audit event naming the poster; given a partial receipt it stays Approved.
7. Given a posted linked receipt is reversed, then the remaining quantity grows back, a Received-closed PO stays Closed, and the reorder suggestion of PL2.6 sees the product again.
8. Statement-count test (from PL1.0): posting an unlinked receipt through the real host issues the frozen number of statements; the oracle fixtures stay green.
9. Submit of a linked receipt re-checks remaining and says so in words; approval re-checks nothing (posting decides, as for stock).

**PL2.6 Reorder suggestions**
1. Given a warehouse with product P on hand 3, safety 10, nothing on order, then the row is `suggestedQty = 2 x 10 - 3 - 0 = 17`; with an Approved PO line of 10 remaining it is 7; with 17 or more on order the row is absent.
2. Given an Approved PO partly received (6 of 10), then on order counts 4; given it is Cancelled or Closed, it counts 0; given it is Draft or Submitted, it counts 0 (not a commitment yet).
3. Given on hand -4, safety 0, then low (negative) and suggested 4 minus on order; given a product with a safety level and no balance row in any warehouse the caller can see, then it is listed with on hand 0; a product stocked only in another warehouse is not listed (the low-stock rule).
4. Given a user scoped to other warehouses, then a warehouse outside the scope is 404; module off 404; no `po.manage` 403; the response carries no cost or value.
5. Statement count: one page costs the low-stock page plus one bounded `IN` statement for on-order; be-dba records the 1M-tier timing (50,000 products, 175,000 balances, 1,000 open PO lines): P95 under 1 s.

## 8. Effort, critical path and calendar

Effort: 16.5 agent-days of build and review, 21.5 with the 25% rework allowance (about 129 agent-hours at 6 hours a day). Backend lane PL2.1 to PL2.6: 2.0 + 3.0 + 2.5 + 3.0 + 2.5 + 1.5 = 14.5 days plus about 0.5 day per PR of merge wait (CI twice, review) = about 17.5 days. The web lane starts at the PL2.3 merge (day 9): PL2.7 to day 11, PL2.8 to 13.5, PL2.9 to 16.5 (its e2e waits for PL2.5 at day 15.5), PL2.10 to 18.5 (needs PL2.6 at day 17.5), PL2.11 to 19.5. **About 20 working days end to end (range 17 to 27).**

Calendar for a part-time team of three (the work is done by agents; the three people decide, review and merge, so the bottleneck is their review time). Three working days a week instead of five multiplies the calendar by about 1.6: full time about 4 weeks, at three days a week about 6.5 weeks. Example, if PL2.1 starts Monday 26 October 2026: done about Friday 20 November full time, about Friday 11 December at three days a week (both before the year-end break; M6 of the lean refresh, Wed 2 Dec, is not moved if the web slices wait for a spare slot). PL2.1 can start before PL1 is fully merged (it needs no open PL1 migration and touches only the catalogs); PL2.5 needs PL1.0 merged.
Honesty note: PL1's nine sub-slices were built within two calendar days (HANDOFFS 2026-10-19 and 2026-10-20), far faster than this method predicts; merging and review are what is still open. These figures are the conservative roadmap method, not a forecast of agent speed; the first real throughput check is the PL1 merge, and the plan is re-estimated then.
