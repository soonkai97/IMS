## 1. Which requirement needs this (lean-scope rule)

No PRD id exists for sales orders, price lists or returns (`TASKS.md` PL3 line): the business-analyst records ids with the owner. Until then the requirement is the owner's ranked market list (ADR section 2).

| Piece | Requirement it serves | Note |
|---|---|---|
| Sales order (create, approve, cancel, close) | ADR R4 "sales and delivery orders"; owner order of 2026-10-19 | What a delivery is checked against; the mirror of the purchase order. |
| Delivery against a sales order, partial deliveries | ADR R4; PRD OUT-01 (Sale), OUT-04 (as quoted in `TASKS.md`) | The delivery IS a core Issue with purpose Sale; the new part is the link and the remaining quantity. |
| Price lists (one default, one optional per customer) | ADR R9 | Second PL3 slice. The price prefills the order line. |
| Returns (customer and supplier) | ADR R6 | Links to a Posted delivery or receipt; the first module with a prerequisite, so `Requires` enforcement is built here. |
| Modules `sales` and `returns` with `CanDisable` / `Requires` | ADR 4.4 ("`purchasing`, `sales`: refuse while any open order"; "`returns`: never refused") | `sales` mirrors `purchasing`; `returns` is where `Requires` finally has a real user. |
| Permissions `so.read`, `so.manage`, `pricelist.manage`, `returns.create` | PRD 3.1 permissions by feature (AUTH-02); ADR section 8 rows 5 and 6 | Approval needs no new permission (D3). The ADR names `so.create`; this plan uses `so.read` / `so.manage` as PL2 did for `po.*` (D4). |
| Approval of a sales order and of a return | BR-06, BR-07 | Reuses `ApprovalRule`, `ApprovalPolicy`, `ApprovalEvaluator`. |

Checklist answers. Simpler way? Yes in seven places, all taken: no `so.approve` permission (D3); delivered and returned quantities are computed, never stored (D5, D14); the delivery carries no selling price (D2); no stock reservation (D6); a return is a document with link columns, not a new aggregate (D12); no separate "list price" column and no new migration for the price audit (D10); the price lookup is a server rule at save, not a configuration screen. New dependency? None. New configuration surface? None: over-delivery and over-return are fixed rules, approval thresholds are the existing Settings rules.
Gap to say plainly: sales orders, price lists and returns are not in the PRD Phase 0 and 1 text that `TASKS.md` quotes; the owner ranked them for the pilot. A re-ranking, recorded here, not scope creep.

## 3. Decisions taken in this plan (not owner questions; be-architect confirms in PL3.2, PL3.3, PL3.5, PL3.15, PL3.16)

| # | Decision | Why, and what it supersedes |
|---|---|---|
| D1 | **A sales order is its own aggregate and its own tables** (`SalesOrder`, `SalesOrderLine`), not a `StockDocument` type. | An order moves no stock; sharing the table would put orders into the movements report, document counts and Home tiles (the PL2 D2 reason). The state machine is copied in shape, not shared in code. |
| D2 | **A delivery is a core Issue with purpose Sale**, created from the order and linked by a nullable `StockDocument.SalesOrderId` and a nullable `StockDocumentLine.SalesOrderLineNo` (1 to n inside the order, frozen once the order is Approved; no foreign key and no index on the line, as built in PL2.4). The delivery carries NO selling price: it values stock at the average cost at posting, exactly like every Issue, and the selling price stays on the order. | The posting engine is untouched. Keeping the price off the delivery means a warehouse user who delivers sees quantities only, and there is one place a price lives. Cost on a delivery is shown to `cost.view` holders exactly as today. |
| D3 | **Approval uses the two tiers.** A new value `DocumentType.SalesOrder = 6`, so `ApprovalRule`, `ApprovalPolicy`, `SelfApprovalNotAllowedRule`, the Settings rule screen and `DocumentNumbering` are reused. No `so.approve`. The rule tests the order TOTAL AT SELLING PRICE and the total base quantity. Deliveries keep the existing Issue approval rule (owner default, question 3). With no sales-order rule an order is released at submit, so (as for `purchasing`) switching `sales` on is refused while no sales-order rule is active, and a data migration writes the two placeholder rules RM 5,000 Standard and RM 20,000 Large only where none exists. | Same reasoning as PL2 D1. Cost, same as PL2: the enum value is not a stock document, so number prefix, `StockDocument.Create`, `StockDirection` and the exhaustive web switches are pinned by tests (risk 4). **Open owner item:** the placeholder amounts are not facts (section 11, question 3), the same open item as the PO amounts in `go-live-checklist.md` section 1. |
| D4 | **Permissions.** `so.read` (Requires `masterdata.read`) and `so.manage` (Requires `so.read`), both owned by module `sales`, group Documents. `so.manage` = create, edit a draft, submit, recall, cancel, close. `pricelist.manage` (Requires `masterdata.read`; owned by `sales`; read and write of price lists). `returns.create` (Requires `document.create`, `stock.read`; owned by `returns`). Approve and reject use `document.approve` / `document.approve.large` (policy `DocumentReview`) plus `so.read` asked in the handler. Creating a delivery needs `document.create` and `so.read`. | PRD 3.1 by feature. Unlike `po.manage`, `so.manage` does NOT require `cost.view`: a selling price is not cost. Any `so.manage` holder may edit any draft order (no ownership split). Defaults: Administrator all four; Supervisor and Clerk `so.read`, `so.manage`; Owner `so.read`, `so.manage`, `pricelist.manage`; Supervisor `pricelist.manage`; Warehouse staff `so.read` only (they deliver); `returns.create` to the holders of `document.create` and `stock.read`. A role gets a row only while it holds what the permission requires (migration rule of PL1.2). |
| D5 | **Delivered quantity is computed, never stored**: ordered base quantity minus the sum of base quantities of Posted delivery lines linked to the order line; a Reversed delivery does not count. A delivery line must use the order line's unit. | PL2 D4 and PL2.4 (5). Cannot drift; a reversal needs no code. |
| D6 | **A sales order reserves nothing.** The stock check stays at posting (the existing negative-stock rule and `stock.negative.override`); over-delivery is refused with the remaining quantity; no tolerance setting. | Owner default, question 1. Reservation would be a new stock concept and a second source of truth. |
| D7 | **Stored order status: Draft, Submitted, Approved, Closed, Cancelled**; "partly delivered" is a derived label. Closing is automatic when the last line is fully delivered (kind Delivered) or manual with a reason of 5 or more characters, allowed only once something has been delivered (with nothing delivered the answer is "cancel it instead", the PL2.5 follow-up rule). A reversal never reopens a Closed order. An open order (for `CanDisable`) is Draft, Submitted or Approved. | PL2 D5. |
| D8 | **Lock order:** `so:{salesOrderId}` is taken before the stock locks, never after, and never together with the roles, modules or document-sequence locks. Taken only when a linked delivery is created or posted, and when an Approved order is cancelled or closed. Returns take `ret:{originalDocumentId}` the same way. Global order becomes: `modules` -> `so:{id}` / `ret:{id}` / `po:{id}` -> document sequence -> document -> stock ascending. | Keeps `ITransactionLocker`'s "fixed order, no cycle" promise (PL2 D12). Whether `so` and `po` may ever be held together: they cannot, no path touches both. |
| D9 | **The client is regenerated inside the backend PR that changes the contract.** No stand-alone contract-batch sub-slice. | PL2 D9; the drift test makes it mandatory. Generated lines count toward the 1,500-line guard; only `web/openapi/**` and migration designers are excluded, so every estimate lists them as "gen". |
| D10 | **Price lists.** `PriceList` (name, optional customer, at most one list per customer, exactly one default) and `PriceListItem` (product, unit, price in RM, 2 decimals, above 0). Lookup for an order line, performed by the SERVER when the order is saved or submitted and exposed read-only for the editor: the customer's list item for (product, unit) if there is one, else the default list's, else none (the person types the price). The price is prefilled; the seller may change it. For every saved line whose price differs from the looked-up list price an audit event `sales-order.price-changed` records order, line, list price, entered price and actor. **No list-price column on the order line**, so no extra migration. A price list never removes or changes a saved order's price. | Owner default question 2 ("every change is audited"). A unit-exact item avoids rounding a per-base price into a per-carton price; no conversion between units is attempted (an order line in a unit with no item has no prefill). |
| D11 | **Selling price visibility.** Order line price, line amount, order total, price-list items and the print of an order are `[VisibleWith(so.manage)]`; a caller with only `so.read` (Warehouse staff) gets quantities and no money, the field absent, not null. The price-list endpoints need `pricelist.manage`. No cost, margin or average cost appears on an order or a price-list screen. `cost.view` is unrelated to selling price. The reviewer who approves needs `so.manage` to see the amount (Supervisor and Owner hold it by default). | A selling price is not cost, so `cost.view` is the wrong gate (`po.manage` needed it because the PO price becomes stock cost). The default that Warehouse staff do not see customer prices is the safe one and costs one attribute to change: owner question N3. |
| D12 | **A return is not a new aggregate.** It is an ordinary draft Receipt (customer return) or Issue (supplier return) carrying a nullable `StockDocument.ReturnOfDocumentId` and a nullable `StockDocumentLine.ReturnOfLineNo`, created by `POST /api/returns` from a Posted original, and it uses the normal draft, submit, approve, post, reverse flow. A return ALWAYS needs one Supervisor approval (Standard tier, `RequiresApproval` true, regardless of amount): the one place that decides is `ApprovalEvaluator`, which receives the link (**unverified** how the evaluator gets its inputs: be-architect confirms in PL3.16; a seeded `ApprovalRule` is not an option because rules are per `DocumentType` and would hit every receipt). | Owner default question 4. Avoids a third copy of the state machine (about 600 lines) and the whole returns reporting question. Cost: the document code has one more link kind to test (statement-count test, risk 5). |
| D13 | **Return costs.** Customer return: the receipt line takes the ENTERED unit cost of the original issue line (same unit, so no rounding), whoever creates it; a typed cost is discarded; stock comes back at the cost the goods left at, and the moving average moves like any receipt. Supplier return: the issue takes the current average as every Issue does. A new value `IssuePurpose.Return = 4` marks the supplier-return issue (a purpose is required on every Issue; `Use` would be misleading in reports). The returned quantity is computed: base quantity of Posted return lines linked to the original line; a Reversed return does not count; over-return is refused. Original must be Posted and not Reversed. | Owner default question 4. **Unverified:** the original line to link by. Document lines have no `LineNo` (read of `StockDocumentLine`): the plan assumes a link by the line's position 1..n in id order, shown as `returnOfLineNo`, or a nullable `ReturnOfLineId` column hidden from the API. be-architect decides in PL3.16 (the id rule says no row ids on lines). |
| D14 | **`returns` Requires `sales` and `purchasing`; `Requires` enforcement is built in PL3.15.** Enable is refused (409 naming the missing module) while a prerequisite is off; a prerequisite cannot be switched off (409 naming the dependent) while a dependent is on; `GET /api/modules` already carries `requires`. Until now no module had a prerequisite, which is why PL2 D7 left it out. `returns` has no `CanDisable` (ADR 4.4: never refused). | A return exists to undo a sale or a purchase and has nothing to link to otherwise. Both are on in the pilot. The cost is that a customer with only `sales` cannot use supplier returns; if the orchestrator wants `Requires` `sales` alone, it is one line in the catalog and one test. |
| D15 | **A line price of 0.00 may be saved on a draft but not submitted** (the PL2 D11 rule): a 0.00 order would pass every amount threshold unseen. Free goods go out as an Issue with purpose Use. | Question N2. |
| D16 | **Closing short, cancelling and who may do what** are one function, `SalesOrderActionPolicy`, feeding `allowedActions`, `canAct` and the handler guards (PL2 pattern). Buttons in the web are exactly `allowedActions`. | PL2 web pattern. |

Why the total is above the band. Four reasons: (1) `Requires` enforcement is new and was not in the re-estimate (650 lines, PL3.15); (2) the price lookup with its audit is a real server rule, not a column (450 lines, PL3.12); (3) rounding every row to half a day adds about 2 days against the sum of lines at the roadmap rates (12,550 lines at those rates is about 31 days with rework); (4) the closing slice. The calibration from PL2 says the true figure is more likely higher than lower (2.3 times the plan), so this plan does not shave. If the owner wants less, cuts in order: (1) the print view of an order in PL3.9 (about 100 lines, new question N1 asks whether it is needed); (2) PL3.14, the editor prefill (250 lines, 0.5 day; the lookup then works only at save and the price is typed); (3) the price-list web screen PL3.13 with an Excel-free "edit items by API only" (650 lines, 1.5 days; not recommended, nobody can use a list without it); (4) the whole of price lists, PL3.11 to PL3.14 (2,150 lines, 6.0 days). ## 6. Acceptance criteria

Given / when / then, one block per sub-slice; each criterion is a named test whose name carries the requirement id (ADR R4 / R9 / R6 until the business-analyst records PRD ids).

**PL3.1 Module and permissions**
1. Given the catalog has `sales`, when a signed-in user calls `GET /api/modules`, then it is listed with `enabled: false`; an Administrator can switch it on with a reason and the audit event is written as for `purchasing`.
2. Given the module is off, then `GET /api/permissions` omits `so.read` and `so.manage`, a role save naming one is a 400 "not available", and a role that holds one keeps it hidden (the PL1.2 generated tests run over the new codes).
3. `so.manage` cannot be saved on a role that lacks `so.read`; `so.read` needs `masterdata.read`. `so.manage` does NOT require `cost.view` (a test pins it: D4).
4. Given a fresh and a migrated database, then Admin holds both codes; Supervisor and Clerk hold both; Owner holds both; Warehouse staff holds `so.read` only; a role without the required permissions gets none; `Down` removes all rows; `SystemRoleDefaults` equals the rows.
5. Architecture: every controller of a module namespace carries `[RequiresModule]`; every endpoint guarded by a module permission sits on that module's controller; `NoRoleDecisionTests` and `EndpointCoverageTests` stay green.

**PL3.2 Sales order core**
1. Given the module on and a caller with `so.manage`, when they POST an order with a customer, a warehouse and lines, then 200 with a Draft, number `SO-<WH>-<yyMM>-0001` (Kuala Lumpur month), lines 1 to n, base quantity converted (BR-04), line amount `round(entered qty x entered price, 2)` half away from zero, total the sum; one audit event.
2. Given 20 parallel creates in one warehouse and month, then the numbers are distinct and gap-free (BR-11).
3. A supplier as customer, an inactive customer, warehouse or product, 0 lines, more than 500 lines, quantity, price or amount above the limits, a price with a fraction of a cent: each is a 400 naming the field (all line errors, not the first).
4. Given a draft, when a `so.manage` holder PUTs it with `If-Match`, then lines are replaced, number and status kept; no header is 428, a stale one 409; an Approved order is not editable (409).
5. Given a caller with `so.read` and no `so.manage`, then list and detail carry no price, amount or total (absent, not null); the DTO coverage test walks the new DTOs and fails if a money field is not annotated; no cost field exists on any sales-order DTO (a reflection test, D11).
6. Given a user scoped to warehouse A, then the list shows only A's orders, an order of B by id is 404, and a create for B is the same 400 as a document's.
7. Module off: 404 for every role on every endpoint, 401 anonymous. On, without the permission: 403.
8. Migration `AddSalesOrders`: Up, Down, Up with rows; Down refuses while an order exists; the model / snapshot test is green; the contract test passes with the regenerated client committed.

**PL3.3 Workflow**
1. Given no active rule, when the creator submits, then the order is Approved at once with `RequiresApproval` false; given a Standard rule at 5,000.00 and an order of 6,000.00, it is Submitted and routed to `document.approve`; given a Large rule it is routed to `document.approve.large` and a Supervisor gets 403.
2. Given a Submitted order, then the submitter cannot approve or reject it (self-approval setting as for documents), another holder of the tier can; reject needs a reason of 5 or more characters and returns the order to Draft; the submitter can recall.
3. Given a line priced 0.00, then submit is a 400 naming the line (D15); a draft with 0.00 saves.
4. Given an Approved order with nothing delivered, a reviewer of its tier can cancel it with a reason; a Draft is cancelled by its creator; a Submitted order by its submitter. (Close short and the refusal of cancel while a delivery exists arrive with PL3.6 and PL3.7, because neither can happen before the link exists.)
5. `allowedActions` for each state and role equals the policy table (generated matrix over the five system roles); `canAct` in the list is true only for a reviewer who may act now.
6. Given `docType = SalesOrder`, then Settings create / update / list work only while `sales` is on (400 on write, hidden in the list while off); every `DocumentType` value has its own number prefix (the default branch answers the Adjust prefix today: pinned); `StockDocument.Create` refuses `SalesOrder`.
7. Each transition writes an audit event with actor, before, after and reason; two simultaneous approvals give one 200 and one 409.

**PL3.4 Module checks**
1. Given no active sales-order rule, when an Administrator switches `sales` on, then 409 with a sentence; with the placeholders present it is 200.
2. Given a Draft, Submitted or Approved order, when an Administrator switches `sales` off, then 409 "N open sales orders: close or cancel them first", no setting change, no audit row; with only Closed or Cancelled it is 200, the data is kept, and on again shows it.
3. A create racing a switch-off does not leave an open order behind a module that is off (the shared form of the `modules` lock, as built for orders in PL2.3b).
4. Migration `AddSalesOrderApprovalRules`: writes the RM 5,000 Standard and RM 20,000 Large rules only where no sales-order rule exists; `Down` removes only those it wrote; a script-only database has them.

**PL3.5 Delivery link**
1. Given an Approved order with lines A (10) and B (5), when a user with `document.create` and `so.read` calls `POST /sales-orders/{id}/delivery`, then a Draft Issue with purpose Sale exists in the order's warehouse for the order's customer, one line per order line with remaining quantity above 0, in the order's unit, each carrying `salesOrderLineNo`, the header carrying the order id and number, and no price anywhere.
2. Given the order is Draft, Submitted, Closed or Cancelled, or has nothing left, then 409 saying which; module off 404.
3. Given a linked draft, when the user saves it, then every line names a line of the same order, the base quantity does not exceed what remains (400 naming the line), customer and warehouse cannot change, lines may be removed or reduced; a save without `salesOrderLineNo` is 400 and the link is intact; naming an order line on an unlinked document is 400; a body that names an order is ignored (tested); with the module off, carrying the field is 400 "not available".
4. A delivery line must use the order line's unit.
5. Migration `AddDeliverySalesOrderLinks`: nullable, no default, filtered index only (model test), Up, Down, Up with rows, Down refuses while a link exists; the DBA records the 1M-tier time in `docs/dba/README.md`.

**PL3.6 Read side**
1. Given 6 of 10 posted through a linked delivery, then the order shows delivered 6 and remaining 4 for that line; reversing that delivery shows 0 and 10. Draft, Submitted, Approved and Cancelled deliveries count as nothing.
2. Given a linked delivery in Draft, Submitted or Approved, then cancel of the order is 409 naming the delivery; a Cancelled or Reversed delivery does not block it.
3. The order detail lists its deliveries (number, status; no money); the delivery GET shows the order number only while the module is on.
4. A deterministic create-vs-cancel race test holds `so:{id}` itself and fails if the call is removed (mutation-proven, as `PurchaseOrderLockTests`).
5. A GET of an unlinked document issues the same SQL statements as before (statement-count test).

**PL3.7 Posting against an order**
1. Given a linked delivery and an Approved order, when it is posted, then ledger and balances are what an unlinked Sale issue of the same lines gives (same rows, same average cost), and the order shows the new delivered quantity.
2. Given the order is Closed or Cancelled, then posting is 409 naming the status and nothing is written.
3. Given 10 ordered, 6 posted, a second delivery of 5, then posting is 409 `OverDelivery` naming product, ordered 10, delivered 6, remaining 4; a warehouse caller sees quantities and no money; nothing is written. A delivery of 4 posts.
4. Given two drafts of 6 against one line of 10 posted at the same time over 25 rounds, then exactly one succeeds each round, the other is 409, and the balance equals the ledger sum.
5. Given parallel posts of linked deliveries and unrelated issues of the same products, then no deadlock is reported (a retried 1205 counts as recovered; the lock order `so` then stock is asserted).
6. Given the last open quantity is delivered, then the order becomes Closed (kind Delivered) in the same transaction with an audit event naming the poster; a partial delivery leaves it Approved.
7. A reversed delivery gives the quantity back and never reopens a Closed order.
8. `POST /sales-orders/{id}/close` (`so.manage`, reason of 5 or more characters) closes an Approved order short only once something is delivered, and not while a delivery is Draft, Submitted or Approved; with nothing delivered it is 409 "cancel it instead".
9. Not enough stock: the delivery post fails exactly as an unlinked Issue does (negative-stock rule unchanged; with `stock.negative.override` it posts).
10. Statement-count test: an unlinked Issue through the real host issues the frozen number of statements; the oracle fixtures stay green.
