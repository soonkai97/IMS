Persona: qa-edge-accessibility. Date: 2026-10-11. Build: current main (web production build http://localhost:4200, API http://localhost:5109, throw-away QA database). Previous report: `docs/qa/edge-accessibility.md` (EA-01..EA-30). Read first: `docs/qa/fix-status-backend.md`, `docs/qa/fix-status-frontend.md`, `docs/qa/retest-power-supervisor.md` (PR-01..PR-14 are not repeated here), `docs/design/mvp-ux.md` (1.2, 1.4, 7.2), `docs/security/refresh-cookie.md`, `docs/security/web-headers.md`.
Roles used: admin, owner, supervisor, staff, clerk (demo users) plus throw-away users `er.*` (second staff, second clerk, user without a warehouse, staff of warehouse 2, second supervisor) and a second warehouse WH02 with posted stock. Passwords and tokens are not recorded here.

## Result in one paragraph

Old findings: 22 fixed, 8 still open (partly fixed, the remainder is listed as ER ids), 0 regressed, 0 not reproducible, 0 waiting only for a product decision (EA-30's "same product on two lines" is the one decision left inside a partly fixed item). New findings: 0 Blocker, 1 Major, 14 Minor, 6 Polish (21 total). The permission model now holds end to end: every document action I tried with each role matched mvp-ux 7.2 (own-only edits, Owner approves Large only, Supervisor cannot approve Large, other-warehouse documents answer 404, `users.read` Admin only, 428 without `If-Match`), the cost rule of 1.4 holds for Staff, Clerk, Supervisor, Owner and Admin on every endpoint and in the UI, and the cookie session, CSRF checks, API security headers and the strict CSP of `web-headers.md` all work. The one serious problem is ER-01: when the session ends while a document is being edited, the user gets an unexplained "Discard changes?" dialog and the typed lines can only be thrown away.

Top 5: ER-01 (session ends during editing: unexplained Discard dialog, work lost), ER-02 (error toasts sit on top of the page's Save button on desktop), ER-03 (keyboard focus is dropped to the page top after every Save draft), ER-04 (empty submit on product, partner and user forms does not move focus; server conflicts are not tied to the field), ER-15 (a deactivated or demoted user keeps full access to the old role for up to 15 minutes, known as SEC-06 but reproduced end to end).

## How this was tested (limits)

- Browser: my own headless Edge driven through the DevTools protocol (the built-in pane has one shared tab): real keyboard events, accessibility tree, viewport emulation (1280x800, 1024, 900, 640x400, 480, 360x740 phone, 320x640 phone, 320x256 = a 1280x1024 window at 400% zoom), light and dark (`prefers-color-scheme`), request interception (401, 429, 500, 504 and network failure on API calls, service worker bypassed for those runs), two tabs in one browser context (sign-out in tab B), network latency emulation. Full page loads were paced to 17 per minute because of the 20 per minute limit; many checks used in-app navigation (history push plus popstate, the same code path as Back and Forward).
- API: Node `fetch` with each role's real token, no extra privilege.
- Strict CSP: a copy of `web/dist/main/browser` with `assets/config.json` set to `{"apiBaseUrl":""}`, served by a small Node server on http://localhost:4300 with exactly the header set of `docs/security/web-headers.md` section 1 and the CSP of section 2 (with and without `upgrade-insecure-requests`), and `/api/*` proxied to the API with only the Origin header rewritten to the allowed web origin (that is what a one-host proxy gives the API). HTTPS, HSTS and the real `Secure` cookie flag cannot be shown on http://localhost.
- Not tested: real screen reader speech (I read the accessibility tree, names, roles, live regions), real touch and soft keyboard, camera scan, real offline mode, Excel download from the browser (it would write a file on this machine; the four exports and both templates were fetched through the API and their header rows read), product import upload through the UI (no file in the sandbox), the `Secure` flag and TLS (security-engineer).
- Environment note: the admin account was locked out ("Too many failed attempts. Try again in 6 minutes.") during my run by five failed admin sign-ins that I did not send (audit rows `login.failed` at 01:36:51, 01:36:52, 01:37:38, 01:37:41 and `login.lockout` at 01:37:58 UTC; my own admin sign-ins before and after worked). It matches SEC-08 (anyone who knows a username can lock it with five requests). It also let me confirm E7 in the UI. No credentials changed.
- Data written to the QA database: one second warehouse WH02 with 100 posted units, users `er.*`, a few dozen cancelled or draft documents, products `ER-LEN*` (name length tests), partners `p...`, two PNG attachments. Settings were restored (negative stock off, self-approval off, cool-down 24).

## 3. The four areas of round one

### 3.1 Keyboard only and screen reader semantics

- Skip link: first Tab stop, visible, Enter moves focus to `main#main-content` (URL gets `#main-content`).
- Order on every screen scanned: skip link, Account, sidebar, page. Visible focus ring on every stop (3px solid, light #1d4ed8 on white 6.70:1 and on the page background 6.19:1; dark #9cc2ff 9.5 to 10.4:1) except the date-picker stop (ER-17). Input borders 4.25:1 light and 6.04:1 dark.
- Route change by keyboard: focus stays on the activated link, the title changes and the `role="status"` announcer says it ("Receipts - IMS"). Acceptable; moving focus to the page `h1` would be better for screen reader users (not logged as a defect).
- Dialogs (Account, More, Approve, Reject, Cancel document, Post, Add item, Discard changes): native modal `<dialog>`, `aria-labelledby` points at the visible title, Esc closes, Tab stays inside (one extra stop leaves to the browser chrome in headless mode), focus returns to the opener. Approve and Post focus the dialog itself (by design for scanners), Reject and Cancel focus the reason box.
- Live regions: "DEMO-001 added." in the Add item dialog, "1 line | 1 unit" totals, "Draft saved.", route announcer; the stale banner is `role="alert"`.
- Accessibility tree sweep of 30 screens in three roles (supervisor desktop 18, admin desktop 5, staff phone 7): 0 interactive nodes without a name, 0 duplicate ids, 0 `tabindex` above 0, 0 images without alt, every table has a caption and `th scope`, exactly one `main` and one visible `nav` name, `lang` follows the language (en, zh, ms). Names that repeat without context: ER-10. Tabs without panel: ER-18.
- Contrast: computed text contrast (foreground against the blended background, 4.5:1, 3:1 for large text) on 19 supervisor and staff screens and 6 admin screens, light and dark: no text below the limit (lowest 6.19 light, 7.56 dark). Text on gradients or images and disabled controls were not measured.
- Quantity and cost fields: `inputmode="decimal"`, `aria-invalid` plus described error on blur: 0, -5: "Enter a quantity above 0."; 1e12-ish: "Enter 1000000000 or less."; 1.23456: "Use at most 4 decimals."; empty or letters: "This field is required."; cost -3: "Enter 0 or more.".

The reports tab strip scrolls sideways at 320 and its second tab starts partly outside the viewport without a scroll cue (not logged: still reachable).
- Remaining layout notes already known: PR-06 (SKU and date wrap in the movements table).

### 3.4 Bad input, stale tabs, double submit, session

- Quantities (UI and API): see 3.1 and EA-18; API refuses 0, -1, 0.00001, 1e12, 1000000000.5, 1.23456, string; accepts 0.0001 and 1,000,000,000; negative cost 400; empty lines 400; same product on two lines accepted (EA-30).
- Duplicate SKU (case-insensitive) 409 "SKU 'demo-001' already exists."; duplicate barcode 409 "Barcode '...' already belongs to another product."; duplicate partner 409 "A supplier named '...' already exists."; duplicate user email 409; the three conflicts reach the user only as toasts (ER-04).
- Malformed requests: bad JSON, empty body, JSON null, wrong content type (415), 2,000 lines, 100,000-character user name: all 400 or 415, no 500; page, pageSize, status, type, warehouse id, date text all validated (400); the exception is the minimum date (ER-06). A 6 MB JSON body resets the connection (ER-21).
- Double submit: Post confirm, three clicks in the same tick: one `POST .../post`. Save draft on a new document: three clicks in the same tick send three `POST /api/documents/receipts` and create three drafts (ER-13); two clicks 120ms apart under 600ms latency send POST then PUT (one document); Enter auto-repeat sends one request.
- Stale document: another user changes a draft, then Save: stale banner with who and when, buttons locked, nothing saved, Reload shows their version (focus detail ER-03). Another user cancels a document, then Approve: banner (focus on the banner), nothing changed.
- Expired token: the first call after expiry is replayed after a silent refresh (round one). When the refresh also fails while a form is dirty: ER-01. Sign-out in another tab does not stop the first tab until its 15-minute access token ends (by design, SEC-06).
- Cookie session: `ims-refresh`: `HttpOnly`, `SameSite=Strict`, `Path=/api/auth`, 7 days, host only (`Secure` is off only because this server is Development over http; documented). Login and refresh JSON `refreshToken: null`. No token in localStorage, sessionStorage, IndexedDB, `document.cookie` or Cache Storage. Refresh without `X-Requested-With`: 403; foreign Origin: 403; no Origin or Referer: 403; look-alike origin `http://localhost:4200.evil.example`: 403; `Origin: null`: 403; Referer of the allowed origin without Origin: 200 (documented); replay of a rotated cookie: 401 and the cookie is cleared; logout without the header: 403, with it: 204 and the cookie is cleared; refresh after logout 401; deactivated user's refresh 401. CORS preflight: the allowed origin gets `Allow-Credentials: true` and the two headers, a foreign origin gets nothing. After sign-out the browser has no cookie and a deep link goes to `/login?returnUrl=...`.

## 5. New security headers (API and strict CSP for the web app)

API, all response kinds checked (200 JSON, 200 xlsx, 401, 403, 404 JSON, route 404, OpenAPI, health): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-site`, the long `Permissions-Policy` (everything disabled), `X-Correlation-Id`, no `Server` header, no HSTS over http (expected). `Cache-Control: no-store` on `/api/auth/*` and `/health`, but authenticated data and the Excel files carry no Cache-Control at all (ER-14).
