### Answers to the probe list
1. **Q5 is the only behaviour change.** Rule `Receipt qty >= 500` created with `roleRequired: "Admin"` is stored and shown as Large/`Owner`. Large document: Staff and Clerk 403 (no permission), Supervisor 403 "above your approval limit", Owner 200, Admin 200. Standard document: Owner 403 "Owners review only large documents", Supervisor 200. Reject routes the same way. Tightening a rule to Large after submit: Supervisor 403, Owner 403, Admin 200. Loosening it (rule inactive) after submit: stored-Large document, Supervisor 403, Owner 200. Self-approval (setting off): Supervisor and Admin approving their own document, standard or Large, 400 "cannot approve a document you submitted". Corrections (recall by non-submitter 403, cancel of an Approved document only by the matching tier 403/200) as before. The Owner never reaches a Standard document and the Supervisor never a Large one. Only the Owner on an Administrator-named rule gained a right. Acceptable under ADR Q5: the Owner already holds the large tier and the audit migration row records the widening.
2. **User API.** Without `users.manage` (Supervisor, Clerk, Staff, Owner): create, update and list all 403. Direct flag: 403 for create, self, other (see finding 1 for the bypasses). Role: unknown, empty, null, number, object, 33 characters, SQL text, `%`, `_`, leading space, tab, newline, zero-width, dotless i, Cyrillic: 400 and no user created; inactive role 400; soft-deleted role 400; a failed update changes nothing (display name, active flag, password, warehouses kept; old password still works). Lax matches: finding 2. Last administrator (not self): demote and deactivate 409, no bypass by spelling. Over-posting (`id`, `publicId`, `roleId`, `passwordHash`, `failedLoginCount`, `lockoutUntil`, `isSystem`, `permissions`, `perm`, `allwh`, `seesAllWarehouses`): ignored, token has only the role's rights.
3. **Rule API.** Create and update need `settings.manage` (Admin only; Owner, Supervisor, Clerk, Staff 403). `approverTier` accepts `Standard|Large` in any case, `1|2`, `"2"`; `0, 3, -1, 99` and every other shape 400; `null` with no role 400. `roleRequired` maps `Owner|Admin` -> Large and `Supervisor|Clerk|WarehouseStaff` -> Standard (exact case; `owner`, `Admin `, NUL, unknown, empty 400); both given must agree (6 disagreeing pairs 400). It cannot move a rule in an unintended way: Large stays Large, Standard stays Standard, and the old `Admin` now equals `Owner` (Q5). Extra properties (`id`, `tier`, `publicId`, `recDeleted`) ignored. The row audit shows the tier change (`{"Tier":"Standard"}` -> `{"Tier":"Large"}`) with the actor; the audit log needs `audit.read` (Owner and Admin 200; Supervisor, Clerk, Staff 403). The migration row holds only a count and rule ids.
4. **Claims.** A custom-role user gets `role=<code>` and its own `perm` list; `allwh=true` has no `wh` claims. Flip the flag off: the old access token keeps `allwh=true` until it expires (as designed), the refresh returns `allwh=false` with `wh`; flip on again, refresh returns `allwh=true`; the used refresh token cannot be replayed (401). Role inactive: new sign-in 401, refresh 401, old access token works until it expires.
5. **Role-name literals in `src/`.** `SystemRoleCodes` is read by: `ApproverTierNames.cs:11,19-20` (translation of the deprecated `roleRequired` to a tier and back; decides nothing else), `ActiveAdminsSpec.cs:9` and `UpdateUserHandler.cs:16` (the last-administrator guard is keyed on the role code `Admin`; a custom role with all rights is not counted as an administrator, which is the safe side), `Seeder.cs`/`SeedDefaults.cs` (first administrator, demo users), `SystemRoleDefaults.cs` (default grants, used by seed and tests). `CurrentUser.Role` is read only to label `/me` (`GetCurrentUserHandler.cs:15-16`). `ClaimTypes.Role` stays the role claim type (`ConfigureJwtBearer.cs:21`) but no `IsInRole` or `Authorize(Roles=...)` exists. Nothing else authorises or scopes by a role name.
6. **Logs and audit.** New audit entries (`user.created`, `user.updated`, row audit) hold username, role code, flag and warehouse ids; no password, hash or token. The row audit now shows `{"RoleId":3}` (internal key) where the old text said the role name; the explicit event carries the code.
