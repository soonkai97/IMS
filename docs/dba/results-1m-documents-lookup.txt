== 1. Documents list: where the plan flips (page statement, no filter, plan compiled fresh for each @p, cache cleared in between; reads of StockDocumentLine) ==
   @p        25    100    150    200    500     800   1,000   1,500   2,000   10,000
   reads  1,318  4,988  7,174  9,590 22,726  36,242  45,206  43,070  43,070   43,070
   CPU ms    16     29     31     47     47      -       -       -     703     719      (compile + execution; 703 ms = the plan that scans the 43,070-page clustered index twice)
   The nested-loop plan costs about 26 reads per document (two correlated SUM subqueries, each a seek and ~6 key lookups); the hash plan costs 43,070 reads whatever the size.
   On THIS database the optimizer flips between 1,000 and 1,500 rows (UPDATE STATISTICS with the default sample did not move it). The API cuts a list at 200 rows
   (Limits.MaxPageSize), so a page the API asks for never compiles to the hash plan here. PR 81 (verification of the public id switch) saw the flip at about 150 rows on a database
   that had been migrated and had taken 14,000 more documents. The threshold is a cost comparison that moves with statistics, row counts and memory; the defect is the cache
   serving the large-page plan to every page size, wherever the flip point sits.
   Reproduction used here ("poisoned"): clear the plan cache of the database, ask the API once for size 25 (the statement is cached), clear again, execute every cached page
   statement once from sqlcmd with TOP(@p) = 2,000 and the session options of the API (ARITHABORT OFF; usecounts and set_options checked in sys.dm_exec_cached_plans: the API reuses that entry),
   then ask the API for 25, 50, 150, 500 (= 200). Script: 23-measure-documents-list.ps1.

== 2. Hint candidates on the page statement (sp_executesql, cache cleared before each hint, steps: poison @p=2,000, then 25, 200, 25; "compile" = SQL Server parse and compile CPU) ==
   no filter                       none                    DISABLE_PARAMETER_SNIFFING     OPTIMIZE FOR UNKNOWN          RECOMPILE
     poison  @p=2000        compile 27, exec 625 ms,43,070    compile 25, exec  94 ms,89,976    compile 15, exec  62 ms,89,976    compile 15, exec 656 ms,43,070
     then    @p=25          exec 610 ms, 43,070 reads         exec   0 ms,  1,318 reads         exec   0 ms,  1,318 reads         compile 26, exec 31 ms, 1,318 reads
     then    @p=200         exec 578 ms, 43,070 reads         exec   0 ms,  9,590 reads         exec   0 ms,  9,590 reads         compile 16, exec 31 ms, 9,590 reads
     then    @p=25 again    exec 547 ms, 43,070 reads         exec   0 ms,  1,318 reads         exec   0 ms,  1,318 reads         compile 16, exec 32 ms, 1,318 reads
   Same picture for the shapes with a warehouse (@w=2), a status (@s=3), a cursor (Id < @olderThan), in every case: shared plan after a poison 390-670 ms and 43,070 reads for
   page size 25 and 200; DISABLE_PARAMETER_SNIFFING and OPTIMIZE FOR UNKNOWN 0-16 ms and 1,130-1,318 reads (25) / 8,660-9,590 reads (200); RECOMPILE 15-32 ms exec, 15-26 ms compile PER CALL.
   RECOMPILE does not repair the large page itself: its own compile at 2,000 rows is the hash plan (625-656 ms); the two other hints give the nested loop plan (62-94 ms).
   Rare values (a hint must not hurt them): status Draft (about 300 rows) 16 ms / 1,352 reads with no hint, 0 ms / 1,352 reads with DISABLE_PARAMETER_SNIFFING; status Reversed (0 rows)
   15 ms / 0 reads either way. The OFFSET shape (page 2 and later: OFFSET @p ROWS FETCH NEXT @p1 ROWS ONLY) stayed on the nested loop plan even for OFFSET 9,800 + 200 (8,942 reads, 31-47 ms),
   no hint needed there; it carries the hint anyway because one specification builds all shapes.
   Chosen: DISABLE_PARAMETER_SNIFFING (the same plan as OPTIMIZE FOR UNKNOWN, but it needs no parameter name, so one line serves every shape of the statement).
   Cost: one compile of 15-34 ms of CPU per cached statement shape (per restart or eviction); 0 ms of compile per request after that. RECOMPILE would cost 15-26 ms of CPU per request for the page.
