== 8. Defects and risks found, all present on main as well (not caused by the switch) ==
D1. GET /api/documents: parameter sniffing on TOP(@p). The page statement (with or without the cursor predicate) compiled for @p >= ~150 gets a hash plan that scans StockDocumentLine twice (44,624 reads, 3.3 s CPU, tempdb spill)
    instead of 590-4,812 reads / 20-120 ms; the plan is then cached and EVERY page size, 25 included, takes 3.3-5.2 s until the plan leaves the cache (restart, statistics update, DBCC FREEPROCCACHE).
    Fresh compile at @p = 25/50/75/100: 95-152 ms; at 150/200/500: 4,370-4,421 ms. After the plan for 200 is cached: size 25 = 5,233 ms (same plan).
    Same on main (documents big-first: 3,935 ms then 4,176 ms for size 25). It hit this run: after the first write-mix run the statistics update recompiled the statement for the k6 setup (pageSize=200) and every later setup walked 100 pages at 3.7 s.
    Hints tried on the statement text (sp_executesql, fresh compile for @p = 200 then 25): OPTION (USE HINT('DISABLE_PARAMETER_SNIFFING')) 137 ms then 2 ms, also 500: 181 ms then 3 ms;
    OPTION (OPTIMIZE FOR (@p = 25)) 130 / 3 ms, 500: 152 / 3 ms; OPTION (LOOP JOIN) 184 / 5 ms but 13.8 s at 500; OPTION (RECOMPILE) does not help the large page itself (its own plan is the hash plan).
D2. GET /api/products/lookup?code=<sku> (document line picker): ProductByCodeSpec is `Sku == code || Barcodes.Any(...)` with TOP(1); the optimizer walks the Product clustered index until the first match, so the cost grows with the position:
    SKU-00042 673 reads / 5-9 ms (what 02 measures), 40 random SKUs: average 963 ms, slowest 2,002 ms (SKU-43564), 79,000 reads per statement x 3 statements per call (Query Store: 1,635 executions of the main-code statement averaged 187 ms and 79,119 reads).
    Same on main. P95 over the catalog is above 1 s on this machine.
D3. GET /api/audit?actor=supervisor: `Actor LIKE @p ORDER BY Id DESC TOP(@p)`: 497,471 reads, 305-330 ms quiet, 0.9-1.0 s P95 in a noisy session, because the 164,176 supervisor rows are far from the newest ones on this database. Equal on main (the stored 2026-10-10 baseline had 9 ms: other data distribution).
D4. Machine sensitivity: GET /api/stock (no filter) scans and sorts all 174,527 balance rows per page (6,068 reads, 195-200 ms P50 in a quiet session); when the laptop slowed down (the same plan, 969 ms CPU instead of ~150 ms) every call took 1.2-1.4 s. Same on main.
